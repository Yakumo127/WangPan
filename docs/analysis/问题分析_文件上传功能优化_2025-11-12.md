# 文件上传功能：问题与优化建议（2025-11-12）

## 背景
- 依据现有实现与文档（时序图、活动图）审阅文件上传流程，聚焦性能、正确性与安全性可改进点。
- 参考：
  - 时序图：`docs/系统设计/时序图/文件上传-UML时序图-20251112-132636.puml`
  - 活动图：`docs/系统设计/活动图/文件上传-UML活动图-20251112-144516.puml`

## 现状梳理
- 后端接口
  - 控制器：`backend/src/main/java/com/filemanager/controller/FileController.java:53`（`POST /api/files/upload` → `FileService.uploadFile`）。
  - 服务：`backend/src/main/java/com/filemanager/service/FileService.java:61` 起，依次执行上传策略与配额校验 → 写盘 → 计算哈希 → 建记录 → 扣减配额 → 审计。
  - 上传策略：`backend/src/main/java/com/filemanager/service/SystemSettingService.java:85`（`isUploadAllowAll` 默认 true），白名单后缀 `getAllowedSuffixes()`（:90）。
- 前端调用
  - 用户侧：`frontend/src/views/files/List.vue` 通过 `@/api/file.uploadFile` 表单直传（支持进度）。
  - 管理端：`frontend/src/views/admin/Files.vue` 使用 `<el-upload action="/api/files/upload">` 简单直传。
  - 示例增强版（分片/秒传/目录上传）在 `config/frontend/src/views/files/List.vue`，但后端未落地对应分片接口。

## 发现的问题（按严重性）
1) 大文件哈希实现存在 OOM 风险与重复 IO
- 现状：`calculateFileHash` 通过 `Files.readAllBytes` 一次性读入内存（`backend/src/main/java/com/filemanager/service/FileService.java:661`）。在允许 100MB+（甚至 1GB）上传时易 OOM；且当前是“先 `Files.copy` 写盘，再全量读取”导致重复 IO。
- 影响：内存峰值大、吞吐低；弱网/大文件下不稳定。

2) 目标文件夹归属未校验（安全）
- 现状：上传时仅 `folderRepository.findById(...)`（`backend/src/main/java/com/filemanager/service/FileService.java:104`），未限制为“当前用户的文件夹”。
- 影响：用户可传入他人 `folderId` 越权绑定文件到非本人目录。

3) 文件落地与数据库一致性缺失
- 现状：`Files.copy` 成功后，若后续建库/配额/审计等任一步失败，会遗留“孤儿文件”。
- 影响：磁盘垃圾文件累积、难追踪清理。

4) 上传策略默认放行
- 现状：`isUploadAllowAll()` 默认 true（`backend/src/main/java/com/filemanager/service/SystemSettingService.java:85`）。
- 影响：生产环境若未配置白名单，易被误允许任意类型；放大内容安全风险。

5) 并发配额校验存在竞态
- 现状：并发请求可能同时通过 `hasEnoughQuota`（`backend/src/main/java/com/filemanager/entity/User.java:120`），随后各自扣减导致超配。
- 影响：用户可在高并发上传下突破额度上限。

6) 内容类型仅依赖后缀/客户端 `contentType`
- 现状：仅做后缀白名单（策略关闭时甚至不校验），保存时 `file.getContentType()` 可能来自客户端头部。
- 影响：易被伪造；危险类型（脚本/可执行）缺少魔数嗅探与拦截。

7) 大文件超时/重试与弱网体验
- 现状：用户侧 `uploadFile` axios 超时 300s（`frontend/src/api/file.js:20`）；失败无分片级重试；不支持断点续传。
- 影响：弱网或大文件易失败，用户体验欠佳。

8) 分片上传/“秒传”能力缺失（前端示例有，后端未落地）
- 现状：有 `FileChunk` 实体（`backend/src/main/java/com/filemanager/entity/FileChunk.java`），但缺少 `uploadChunk/merge/checkFileExists` 等接口与服务；`config/frontend/src/views/files/List.vue` 中调用了 `fileApi.checkFileExists`/`uploadChunk`/`uploadFile` 等占位方法，但后端无响应实现。
- 影响：无法支撑大文件稳定上传与秒传/去重需求。

9) 配置不一致与用户侧预检不足
- 现状：`backend/src/main/resources/application.yml` 限制 `spring.servlet.multipart.max-file-size: 100MB`，而脚本/文档里存在 1GB 的开发配置（`scripts/application-dev.yml`）。
- 影响：环境切换时行为不一致；前端在选择文件时未主动对后端限制做友好提示。

10) 存储目录平铺，单目录文件数增长风险
- 现状：路径为 `{storagePath}/user_{uid}`，所有文件存放同一层级。
- 影响：文件数增长后单目录操作退化；备份/迁移成本上升。

11) 病毒扫描与审计/指标的可观测性可加强
- 现状：上传成功已记审计（`backend/src/main/java/com/filemanager/service/FileService.java:129`），失败与策略拒绝原因覆盖有限；缺少上传路径的指标（耗时/体量/错误码分布）。
- 影响：运营排查与安全对抗不够友好。

## 优化建议（按优先级）
【高优先级】
- 流式哈希与单次 IO：用 `DigestInputStream`（或循环 buffer）边写盘边计算哈希，替代 `readAllBytes`（参考：`FileService.java:95`, `FileService.java:661`）。
- 目标文件夹归属校验：改为 `FolderRepository.findByIdAndUserIdAndDeletedFalse(...)` 并拒绝越权（`FileService.java:104`）。
- 失败清理与两阶段落盘：出错时 `Files.deleteIfExists(filePath)`；或先落临时文件名，DB 成功后原子 `move` 为最终名。
- 策略默认安全：将 `isUploadAllowAll()` 默认设为 false（`SystemSettingService.java:85`），上线前要求配置后缀白名单；无后缀文件可根据策略拒绝或特殊处理。
- 配额扣减原子性：用 DB 原子更新（受影响行数校验）或乐观锁/分布式锁，避免并发越额（`User.java:120`）。

【中优先级】
- 分片上传/断点续传：落地 `init/check/uploadChunk/merge` 等接口，结合 `SystemConfig.KEY_CHUNK_SIZE`；前端失败重试、并发片上传、断点续传与“秒传”。
- 内容安全：在白名单基础上增加 MIME/魔数检测，屏蔽可执行与脚本类危险类型，返回 400/415 统一错误体。
- 大小限制与错误处理：统一环境 `max-file-size`，前端选择前做本地校验；后端捕获 `MaxUploadSizeExceededException` 返回一致的 JSON。
- 路径分层：以 `fileHash` 前缀散列二级目录（如 `ab/cd/...`），控制单目录规模；缩略图目录已分层可复用思路。

【低优先级】
- 病毒扫描：按需接入（如 ClamAV），策略化启用；失败拒绝并审计。
- 审计与指标：补充失败事件与拒绝原因；暴露上传耗时/大小/错误分布到 `/actuator/metrics` 方便观测。

## 建议的最小改动路线（可分阶段落地）
1. 替换哈希实现与写盘逻辑，实现“单次 IO + 流式哈希”，并在 `uploadFile` 内用 try/catch 兜底清理落地文件。
2. 上传 `folderId` 改用归属校验查询；无权限/不存在统一错误语义。
3. 将上传策略默认改为更安全（默认 `allowAll=false`），并在管理端完善白名单设置入口（已有“管理员-系统设置与上传策略”对齐）。
4. 针对配额并发：实现原子扣减（或锁）。
5. 视业务需要，补齐分片/秒传接口与 `FileChunk` 读写流程，并对接前端示例。
