# 存储与垃圾分片清理实现注意事项（2025-11-20 20:25）

> 本文仅记录在实现“存储与垃圾分片清理”功能时需要特别注意的点，作为设计与编码阶段的风险提示与检查清单。完整功能设计见后续专门的规格文档（specs）。

## 一、整体功能范围回顾

- 新增一块“存储与空间”能力，挂在系统设置页中，与“系统信息”同级，仅对管理员可见。
- 页面功能包括：
  1. 展示当前项目（整个系统）使用的硬盘空间大小；
  2. 展示“垃圾分片”（超过 1 小时未合并且无活跃上传任务的分片文件）总大小；
  3. 用表格按“用户”归纳垃圾分片数量与占用空间；
  4. 提供“全局手动清理”按钮以及“按用户清理垃圾分片”按钮，集成显式的分片清理 API。

## 二、后端侧注意事项

### 2.1 “整个项目硬盘空间”的统计口径

1. 明确统计范围：
   - 建议将“项目硬盘空间”限定为 **应用文件存储目录**（例如 `storagePath`）及其下的正式文件 + Blob + 分片等内容；
   - 不建议将数据库文件、容器日志、系统级日志等纳入此处统计，否则口径会与“应用可控空间”混在一起，难以解释。

2. 统计方式：
   - 避免每次请求都做完整目录递归扫描（在数据量大时会较慢）：
     - 可考虑在后台周期性扫描并缓存结果；
     - 或在文件上传/删除时维护累加统计值，并在必要时提供“全量重建”能力。
   - 对“垃圾分片”统计可以与清理逻辑共用一次遍历，避免重复 IO。

### 2.2 “垃圾分片”判定逻辑

1. 判定条件：
   - 分片文件存在路径：`{storagePath}/chunks/user_{uid}/{fileHash}/chunk_x.part`；
   - 该分片对应的 fileHash 在 **最近 1 小时内没有新的分片写入**（以 `mtime` 或记录时间为准）；
   - 同时“没有活跃上传任务”：
     - 简化做法：仅靠时间 + 分片存在判定；  
     - 理想做法：结合上传任务状态（如上传任务/会话表），避免误判正在重试中的上传。

2. “活跃上传任务”的实现：
   - 现阶段没有独立的“上传任务表”时，可暂时按以下策略：
     - 仅以分片目录最近修改时间（`mtime`）为主；
     - 加上 1 小时缓冲窗口，降低误删概率。
   - 若后续引入上传任务记录（如 `upload_sessions` 表）：
     - 优先使用该表判断某个 `userId + fileHash` 是否仍有状态为“进行中”的任务；
     - 与分片目录的时间信息结合，提高准确性。

3. 极端场景：
   - 服务器时间跳变（NTP 校时或手工改时间）可能影响“超过 1 小时”的判断；
   - 若存储分布在多台机器，需要保证 `mtime` 均出自同一时间源，或引入显式时间戳记录。

### 2.3 清理 API 的安全性

1. 权限控制：
   - 清理接口必须加上管理员权限保护（如 `@PreAuthorize("hasAuthority('ROLE_ADMIN')")`）；
   - 即便前端仅在“系统设置（管理员）”中使用，也不能依赖前端做权限限制。

2. 清理范围协调：
   - 全局清理：
     - 删除所有满足“垃圾分片”条件的分片目录/文件；
     - 注意不要清理当前正在合并（merge）的临时文件；
   - 按用户清理：
     - 仅删除对应 `userId` 的 `chunks/user_{uid}/...` 目录中符合垃圾条件的分片；
     - 不影响其他用户。

3. 并发与一致性：
   - 清理过程中可能有新的上传开始，应避免误删刚开始的分片：
     - 清理逻辑应以“当前时间 - 1 小时”为界，严格过滤掉最近 1 小时内写入的分片；
     - 对于恰在边界附近的文件，可以通过二次检查（例如再次确认没有新的 chunk_x.part 被创建）来降低误删概率。

4. 审计与日志：
   - 建议在清理操作中记录：
     - 操作人（管理员 ID/用户名）；
     - 清理时间；
     - 清理模式（全局 / 某个用户）；
     - 清理掉的分片数量与释放空间大小；
   - 便于后续问题追踪与运维审计。

## 三、前端侧注意事项

### 3.1 新页面位置与权限

1. 页面位置：
   - 新 Tab 名称建议为“存储与空间”或类似表意明确的名称；
   - 与“系统信息”同级，放在系统设置页（`System.vue`）的 Tab 中。

2. 权限与路由：
   - 前端应只在管理员登录时显示该 Tab（可根据当前用户角色判断）；
   - 路由与菜单部分需保证非管理员无法通过 URL 直接访问该页面（即使访问，后端也会拒绝）。

### 3.2 统计信息展示

1. 顶部总览区域：
   - 当前项目文件总占用空间，例如：“总文件占用：123.45 GB”；
   - 垃圾分片总占用空间，例如：“垃圾分片：1.23 GB”；
   - 一个全局清理按钮（“清理所有垃圾分片”）。

2. 用户级表格：
   - 字段建议：
     - 用户名 / 显示名；
     - 垃圾分片数量；
     - 垃圾分片总大小；
     - 最早分片产生时间（oldest）；
     - 最新分片产生时间（newest）；
   - 操作列：
     - “清理该用户垃圾分片”按钮，触发按用户范围的清理 API。

### 3.3 清理操作的交互与文案

1. 确认弹窗必需明确高风险：
   - 全局清理提示建议：
     > 将清理所有“超过 1 小时未合并且无活跃上传任务”的分片文件，本操作不可恢复。  
     > 预计可释放约 X GB 磁盘空间，是否继续？
   - 按用户清理提示建议：
     > 将清理该用户所有“超过 1 小时未合并且无活跃上传任务”的分片文件，本操作不可恢复。  
     > 预计可释放约 Y GB 磁盘空间，是否继续？

2. 清理过程中的状态反馈：
   - 清理按钮在请求期间应显示 loading 状态，防止重复点击；
   - 成功后刷新统计数据与表格；
   - 若清理失败，应给出后端返回的错误信息，并引导管理员查阅系统日志。

### 3.4 与上传逻辑的协同

1. 界面一致性：
   - 上传队列与垃圾分片统计应遵循一致的目录与哈希规则（`chunks/user_{uid}/{fileHash}`）；
   - 前端不直接操作分片路径，统一通过后端统计与清理接口交互，避免耦合。

2. 极端情况：
   - 当管理员清理垃圾分片的同时，有用户恢复了一个“很久没传完”的大文件：
     - 若该文件的分片已被清理，后续分片上传与 merge 将失败，需要在上传逻辑中有清晰的错误提示，例如：
       > “上传所需的分片已失效，请重新开始上传。”

## 四、接口与实现顺序建议（简要）

> 细节在专门的规格文档中设计，这里只给出后续实现时的顺序建议。

1. 后端：
   - 增加统计接口：返回总文件占用 + 垃圾分片总占用 + 按用户归纳的垃圾分片统计；
   - 增加清理接口：
     - 全局清理垃圾分片；
     - 按指定用户清理垃圾分片。

2. 前端：
   - 在系统设置中新增“存储与空间” Tab，调用统计接口展示数据；
   - 接入全局/按用户清理按钮，配合确认弹窗与 loading 状态；
   - 与上传队列界面保持文案与行为一致，避免用户产生误解。

本注意事项文档作为后续“存储与垃圾分片清理”功能设计与实现的风险清单使用，具体接口定义与页面交互细节将在 specs 文档中给出。
