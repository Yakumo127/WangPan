# 文件预览请求长期未完成问题复盘（2025-11-20 16:31）

## 一、问题现象（从用户视角）

1. 触发场景  
   - 在系统页面（已登录）点击某个 PDF 文件名，前端路由跳转到预览页 `/preview/:id`。

2. 浏览器 Network 观察到的现象  
   - `GET /api/files/{id}/preview`：
     - 状态码：`200 OK`；
     - `Content-Type: application/pdf`；
     - 大小：约 158KB；
     - 时间分解：等待服务器响应 ~100ms，内容下载 ~150ms，总耗时 ~260ms；
   - 但在 Network 的详细信息中可以看到提示：
     > “注意：请求尚未完成！”
   - 这表明：**浏览器已经收到了状态码和部分/全部响应体，但 HTTP 连接在浏览器看来仍然处于“未完成”状态**。

3. 页面体验  
   - 预览页始终显示“加载中”（转圈），长时间不结束；
   - DOM 树中查找不到 `<div class="pdf-viewer">` 节点，说明前端的 pdf.js 组件 `PdfViewer` 并未被真正挂载；
   - 同时，用户从预览页返回“文件管理”时，`/api/files/list`、`/api/folder/list` 等接口偶发 10 秒 Axios 超时（`timeout of 10000ms exceeded`），进一步强化了“系统卡住、一直转圈”的感受。

从用户视角，问题可以概括为一句话：  
> 预览接口显示 200 且文件大小正常，但请求迟迟不结束，预览页面一直在转圈。

## 二、技术实现现状（出问题前）

### 1. 后端预览接口实现方式

预览接口为：

- URL：`GET /api/files/{fileId}/preview`；
- 主要逻辑：
  - 校验登录态与权限（普通用户 / 管理员）；
  - 校验扩展名是否包含在预览白名单；
  - 通过 `file.getFilePath()` 定位物理文件路径；
  - 使用 `StreamingResponseBody` 将文件内容写入响应：

```java
StreamingResponseBody body = outputStream -> {
    long started = System.currentTimeMillis();
    try (InputStream in = Files.newInputStream(filePath)) {
        byte[] buffer = new byte[8192];
        int len;
        while ((len = in.read(buffer)) != -1) {
            outputStream.write(buffer, 0, len);
        }
        auditLogService.logSuccess(..., "预览成功", System.currentTimeMillis() - started);
    } catch (Exception ex) {
        auditLogService.logFailure(..., "预览过程中流传输出错", ex.getMessage(), ...);
        throw ex;
    }
};

return ResponseEntity.ok()
        .contentType(MediaType.parseMediaType(contentType))
        .header(HttpHeaders.CONTENT_DISPOSITION, disposition) // inline
        .header(HttpHeaders.CACHE_CONTROL, "no-store")
        .header("X-Content-Type-Options", "nosniff")
        .body(body);
```

特点：

- 使用 streaming 方式输出文件内容；
- **未显式设置 `Content-Length`**，由容器与代理自行决定如何处理流式响应。

### 2. 前端预览实现方式

1. 请求层  
   - 使用封装的 `request.js`（Axios 实例），在 `responseType === 'blob'` 情况下直接返回原始响应；
   - `previewFile(id)` 实现：
     ```js
     export function previewFile(id) {
       return request({
         url: `/files/${id}/preview`,
         method: "get",
         responseType: "blob",
         timeout: 0
       })
     }
     ```

2. 预览页面 `Preview.vue`  
   - `onMounted` 时调用：
     ```js
     const res = await previewFileApi(fileId.value)
     const blob = res?.data
     // 根据扩展名 / Content-Type 判定 viewerType（pdf / text / video / office / unknown）
     // PDF 情况下：blob.arrayBuffer() → Uint8Array → 交给 PdfViewer 渲染
     ```
   - 外层使用 `v-loading="loading"` 控制 loading 状态，`loading` 在 `finally` 里关闭。

3. pdf.js 渲染组件 `PdfViewer.vue`  
   - 接收 `Uint8Array` 的 PDF 数据，使用 `pdfjs-dist` 解析并将每页绘制到 `<canvas>`；
   - 使用 `GlobalWorkerOptions.workerSrc` 指向 pdf.js 官方 CDN（后续又暴露出 worker 不能加载的问题，此处暂不展开）。

简化理解：  
> 前端高度依赖 `/preview` 这个请求“按时完成且返回完整 Blob”，否则 `await` 会一直挂起，loading 就不会结束。

## 三、问题根因分析

### 1. HTTP 连接语义不明确：Streaming + 无 Content-Length

在当前部署环境中，预览接口的 HTTP 响应链路大致如下：

> Spring Boot 应用 → 反向代理 / 网关（18800）→ 本地代理（10808）→ 浏览器

预览接口使用的是 streaming 方式输出数据，但没有设置 `Content-Length`，实际行为依赖“服务端在写完数据后关闭连接”，代理和浏览器据此判断响应结束。

然而在这条链路中，结合 Network 面板的观察：

- 浏览器已经看到了：
  - 响应头（200 + Content-Type）；
  - 完整或大部分响应体（约 158KB）；
- 但请求依旧显示为“尚未完成”，说明：
  - 在链路某一环节（可能是应用容器、反向代理或本地代理），连接没有被明确关闭；
  - 或者 streaming 响应被某个中间层以“长连接/缓冲”的方式处理，导致浏览器认为响应仍在进行中。

**换句话说：对于浏览器和 Axios 来说，`/preview` 这条请求完成的必要条件——“连接被明确结束”——迟迟没有发生。**

### 2. 前端等待模型放大了问题

前端的预览逻辑是以 `await previewFileApi(...)` 为起点的一整套流程：

- 如果 `/preview` 请求完成：
  - Promise resolve，进入后续逻辑：
    - 判定 `viewerType`；
    - 构造 `pdfData` 或 `blobUrl`；
    - 更新 DOM（挂载 `<PdfViewer>` 或 `<iframe>`）；
    - 在 `finally` 中将 `loading=false`，结束转圈。

- 如果 `/preview` 请求**长期处于“未完成”状态**：
  - `await` 永远等不到结果；
  - `try/catch/finally` 整体不执行或非常延后；
  - 页面一直处于 `loading=true` 的状态；
  - DOM 中不会出现 `<PdfViewer>`（因为 pdfData 迟迟未赋值），用户看不到任何变化。

因此，后端 streaming 响应的问题，被前端「强依赖请求完成」的等待模型放大成了用户体验上的“永远转圈”和“似乎一直在下载”的现象。

### 3. 与已验证下载链路行为不一致

对比预览与下载接口：

- 下载接口（包括直链下载）统一通过 `buildDownloadResponse(...)` 实现，特点：
  - 会计算 `Files.size(filePath)`；
  - 设置 `Content-Length`；
  - 进行路径归属存储根目录的安全检查；
  - 更新 blob 最近访问时间与下载 metrics。

- 下载行为在现网环境中表现稳定：浏览器能正确显示下载进度并在读取完内容后结束连接。

- 预览接口则使用了一条单独的 streaming 路径：
  - 不设置 `Content-Length`；
  - 不复用 `buildDownloadResponse` 的路径安全检查与 metrics；
  - 在当前代理链路下表现出“请求不结束”的问题。

**这说明：预览接口在传输层的实现方式，相比下载链路要“更脆弱”，是问题的根源之一。**

## 四、解决方案与调整思路

### 1. 目标

1. 从 HTTP 语义层面保证：
   - `/api/files/{id}/preview` 在发送完整内容后，响应能够在合理时间**明确结束**；
   - 浏览器和 Axios 能可靠地将该请求视为“完成”，从而继续执行前端渲染逻辑。

2. 从安全与可维护角度保证：
   - 预览接口具备与下载接口相同级别的路径安全校验；
   - 保留/增强审计日志，便于追踪预览行为；
   - 为后续预览功能演进留下空间（例如单独 metrics、限流等）。

### 2. 方案选择：弃用 StreamingResponseBody，改用 Resource + Content-Length

基于上述目标，最终选定的方向是：

1. **不再使用 `StreamingResponseBody`**：  
   避免“应用自行管理 streaming 输出”的复杂度，将输出流管理交还给 Spring MVC/Tomcat。

2. **使用 `Resource + contentLength` 返回文件内容**：
   - 通过 `FileSystemResource` 封装文件；
   - 通过 `Files.size(filePath)` 获取文件大小，并设置为 `Content-Length`。

3. **补齐路径安全与错误处理**：
   - 路径必须归属于存储根目录（防止目录穿越）；
   - 明确区分 404/403/400 等错误场景，并记录审计日志。

### 3. 实际后端调整要点（简述）

> 代码详细见 `backend/src/main/java/com/filemanager/controller/FileController.java` 中 `previewFile(...)` 最新实现。

1. 方法签名调整：

```java
@GetMapping("/{fileId}/preview")
public ResponseEntity<Resource> previewFile(@PathVariable Long fileId,
                                           HttpServletRequest request) { ... }
```

2. 上层认证、权限、预览后缀白名单校验保持不变。

3. 路径与文件校验补齐：

```java
Path filePath = Path.of(file.getFilePath());
if (!Files.exists(filePath) || !Files.isReadable(filePath)) {
    // 记录“物理文件不存在或不可读”，返回 404
}

Path root = Paths.get(fileService.getStorageRoot()).toAbsolutePath().normalize();
Path normalized = filePath.toAbsolutePath().normalize();
if (!normalized.startsWith(root)) {
    // 记录“非法文件路径”，返回 403
}

long totalSize = Files.size(filePath); // 结合 NoSuchFile / AccessDenied / IOException 分别处理
```

4. 构造 Resource 响应：

```java
Resource resource = new FileSystemResource(filePath.toFile());
auditLogService.logSuccess(..., "预览成功", System.currentTimeMillis() - start);

return ResponseEntity.ok()
        .contentType(MediaType.parseMediaType(contentType))
        .header(HttpHeaders.CONTENT_DISPOSITION, disposition) // inline
        .header(HttpHeaders.CACHE_CONTROL, "no-store")
        .header("X-Content-Type-Options", "nosniff")
        .contentLength(totalSize)
        .body(resource);
```

通过 `.contentLength(totalSize)`，代理和浏览器都能明确知道“应该读取多少字节”，从而在读取完毕后正确结束响应，Axios 外层的 `await` 也可以可靠 resolve。

## 五、经验教训与后续建议

1. **流式响应要谨慎在含代理链路中使用**
   - StreamingResponseBody 适合大文件、持续推送等场景，但需要确保：
     - 所有中间层（网关、代理、WAF）的 streaming 支持良好；
     - 即使不设置 Content-Length，也能可靠地通过连接关闭来标识响应结束。
   - 在代理链路不完全可控的环境中，更安全的做法是：
     - 尽量使用 `Resource + contentLength` 这类常规响应模式；
     - 将 streaming 使用限制在必要场景，并单独验证。

2. **前端等待模型要考虑“请求永不结束”的情况**
   - 当前预览逻辑是一个典型的“单请求驱动整个渲染”的模型，这种模型简洁但对后端请求的健壮性要求很高；
   - 在未来可以考虑：
     - 对 `await` 加入额外的超时/兜底逻辑（例如 30 秒内未完成则给出明确提示）；
     - 对异常或长时间未完成的请求在 UI 上给出更明确的状态，而不是一味转圈。

3. **复用已有“已验证路径”可以大幅降低风险**
   - 下载链路已经通过现网验证相对可靠，预览本可以在传输层上尽量复用下载链路的实现（仅在行为上改为 inline）；
   - 未来在设计新接口时，优先考虑复用已验证的子系统（例如统一的文件读取与响应构造逻辑），能明显降低“环境相关”的问题。

4. **文档与复盘的重要性**
   - 本次问题跨越了后端 HTTP 语义、代理行为与前端等待模型三个层面，单看任何一层都容易误判；
   - 通过完整复盘文档记录问题现象、实现现状、根因分析与解决方案，有助于：
     - 后续排查类似问题时迅速联想；
     - 指导新功能设计时避免重蹈覆辙；
     - 为团队成员提供可参考的案例。
