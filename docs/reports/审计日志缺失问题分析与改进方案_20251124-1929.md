# 审计日志缺失问题分析与改进方案（2025-11-24 19:29）

## 问题成因
- **异常被吞导致未落库**：`AuditLogService.save` 内部捕获所有异常直接忽略，且当传入 `userId` 为空又查不到 `system/admin` 用户时直接返回，匿名/系统级失败日志会被静默丢弃。
- **切面静默忽略 SpEL/持久化错误**：`ServiceAuditAspect` 与 `ApiAuditAspect` 的 `catch (Exception ignore)` 抑制了 SpEL 解析或持久化异常，导致日志写入失败无告警，问题无法追踪。
- **业务覆盖面空洞**：`UserService` 的注册/资料更新/改密等方法未加 `@AuditedOperation`，控制器层又在 try-catch 内直接返回 4xx，导致成功/失败均不记审计。
- **匿名/系统操作缺少兜底账号**：若数据库不存在 `system`/`admin` 用户，系统级日志直接被跳过，没有后备写入主体。

## 排查过程与历史
1. 检查审计切面与服务实现：
   - `AuditLogService.save` (backend/src/main/java/com/filemanager/service/AuditLogService.java) 捕获异常后忽略，且用户解析失败即返回。
   - `ServiceAuditAspect` / `ApiAuditAspect` (backend/src/main/java/com/filemanager/audit) 也对异常统一 `ignore`。
2. 审计覆盖点梳理：
   - `@AuditedOperation` 主要出现在文件服务、部分系统设置与登录接口，注册/改密等未覆盖。
   - 控制器（如 `AuthController`）内部捕获异常返回 400，不会触发 `ApiAuditAspect` 的异常切点。
3. 配置核对：
   - `audit.success-fallback.enabled=true` 仅兜底 GET 成功，但对 try-catch 失败无覆盖。
4. 现象总结：
   - 匿名访问、调度任务异常、注册/改密失败等场景无审计记录，也无错误日志提示。

## 修复建议
- **提高可观测性**：切面与 `AuditLogService` 遇到 SpEL/持久化异常时打印告警日志（含 action、userId、表达式、异常栈），避免静默失败。
- **兜底主体**：在解析不到用户时自动创建/回退到内置 `system` 账号，保证系统级日志可落库。
- **补齐注解覆盖**：为注册、资料更新、改密等关键业务添加 `@AuditedOperation`；对捕获异常后返回 4xx 的路径，在服务层抛出业务异常让切面感知，或在 catch 内显式调用 `auditLogService.logFailure`。
- **异常链保留**：`AuditLogService.logFailure` 限长截断后仍应保留完整堆栈到告警日志，方便排查。
- **运行期监控**：暴露 “审计写入失败计数” 指标，配置告警；确保定时清理任务保留系统级审计记录。

## 实际需实施的修复操作（建议落地顺序）
1) 修改 `AuditLogService.save`：告警日志记录失败原因；用户解析失败时回退 system；保留错误信息。  
2) 修改 `ServiceAuditAspect` / `ApiAuditAspect`：捕获异常改为 warn/error 日志，并在 SpEL 解析失败时写一条系统级失败审计。  
3) 补充 `@AuditedOperation`：注册/改密/资料修改/关键后台任务。  
4) 线下联调：验证匿名访问、注册失败、调度异常等场景均有审计记录并含错误信息。
