# 下载直链与一次性 Token 设计方案（2025-11-20 11:44）

本文在现有“文件下载功能”基础上，针对“浏览器原生下载体验不足、大文件易受前端超时限制”等问题，给出一套基于**短期、一次性下载 Token 的下载直链方案**。方案满足：

- 点击下载后由浏览器直接发起真实 HTTP 下载请求，显示浏览器自带下载进度条；
- 下载链接仅在生成后短时间内有效（建议 10 秒）；
- 每个下载链接最多只允许成功下载一次；
- 权限控制仍基于现有用户体系与文件权限模型。

## 一、问题成因

### 1.1 现有实现方式回顾

- 前端通过 Axios 直接请求下载接口：
  - 早期方案：`axios.get('/api/files/download/{id}', { responseType: 'blob' })`。
  - 后续优化：改为 `fetch('/api/files/download/{id}') + Blob + a.click()`，避免 Axios 的 10 秒超时。
- 下载流程：
  1. 前端 JS 发起请求，获取完整响应体并缓冲到内存；
  2. 使用 `Blob` 和 `URL.createObjectURL` 创建临时 URL；
  3. 通过动态创建 `<a>` 元素并触发 `click()` 启动浏览器保存对话框。

### 1.2 暴露出的核心问题

1. **浏览器原生下载体验缺失**：
   - 由于下载是由 JS 管理的，浏览器认为“网络请求”已经结束，后续只是本地 Blob 保存操作；
   - 用户看不到浏览器右上角 / 底部的“下载进度条/下载任务列表”，仅能在界面上看到我们自定义的提示。

2. **大文件下载易受前端限制**：
   - 即便改用 fetch，也需要前端拉完整个响应体再触发保存，整体内存占用较大；
   - 若未来支持百 MB / GB 级文件，前端持有完整 Blob 的方式并不理想。

3. **安全性与权限控制前后分离**：
   - 当前权限控制完全依赖“下载请求由前端带 JWT/Header 发起”的模型；
   - 若想让浏览器“原生下载”一个 URL，就需要在后端支持“不依赖前端 JS 注入 Header”的下载方式。

综上，现有方案虽然解决了 Axios 超时问题，但仍存在体验和可扩展性不足，需要在架构上进一步演进。

## 二、排查过程与历史

1. **初始问题：6MB 文件下载 Axios 超时**
   - 现象：
     - 下载约 6MB 文件时，控制台报错：`AxiosError: timeout of 10000ms exceeded`，code 为 `ECONNABORTED`；
     - Network 面板中请求状态为 `200 OK`，数据传输完整；
     - 说明前端因为 Axios 超时主动中断了请求，而后端实际上正常返回。
   - 原因：
     - Axios 全局实例使用了 `timeout: 10000`；
     - 下载接口未单独配置 timeout，大文件在当前链路环境下容易超过 10 秒阈值。

2. **第一次修复：改为 fetch + Blob + a 链接**
   - 调整：
     - 不再通过 Axios 发起下载请求；
     - 改为使用 `fetch('/api/files/download/{id}', { headers: { Authorization: Bearer token } })` 拉取 Blob，再用 `a.click()` 启动保存；
     - 修复了“10 秒超时导致下载失败”的问题。
   - 新反馈：
     - 用户观察到：点击下载后，Network 中的请求长时间显示为“挂起（Pending）”，随后一次性完成；
     - 浏览器未显示原生“下载进度条 / 下载任务列表”，体验与其他网站的下载有所差距。

3. **第二轮诉求：接近网盘产品的原生下载体验**
   - 用户期望：
     - 点击下载后，浏览器应该立即显示一个下载任务，并能看到下载进度；
     - 同时确保下载权限与安全性不下降，甚至更严格。
   - 技术结论：
     - 要达到这一体验，必须让浏览器以“普通 URL 下载”的方式工作（例如直接访问一个带 `Content-Disposition: attachment` 的 URL），由浏览器自己管理下载任务；
     - 这要求后端提供一种**不依赖前端传入 JWT Header 的安全下载机制**。

4. **方案方向选择**
   - 对比多种方案后，最终选择：
     - 前端点击下载 → 先请求一个“下载 URL 生成接口”；
     - 后端为当前用户和目标文件生成一个**短期、一次性下载 Token**，封装在一个下载 URL 中返回；
     - 前端拿到 URL 后直接 `window.open(url)`，由浏览器原生发起下载。

## 三、修复建议：下载直链与一次性 Token 方案设计

本节给出完整的技术设计，包括整体流程、Token 结构、后端与前端改造点，以及“10 秒有效 + 单次使用”的具体实现方式。

### 3.1 整体流程

1. 用户在前端点击某个文件的“下载”按钮；
2. 前端调用轻量接口（走 JWT）：
   - 普通用户：`GET /api/files/{fileId}/download-url`
   - 管理员：`GET /api/files/admin/{fileId}/download-url`（如有需要单独接口）
3. 后端在该接口中：
   - 从 SecurityContext 获取当前登录用户；
   - 调用 `fileService.getFileForDownload(fileId, userId)` 做一次权限与存在性校验；
   - 生成一个包含 `fileId`、`userId`、`exp`、`nonce` 等信息的下载 Token，并用 HMAC-SHA256 签名；
   - 将 token 放入一个下载 URL，例如：`/api/files/direct-download?token=<token>`，连同过期时间返回给前端。
4. 前端拿到 `url` 后，直接调用：
   - `window.open(url, '_blank')`，或
   - 动态创建 `<a href="url" download>` 并触发点击；
   浏览器将此 URL 视为普通文件下载，自动显示原生下载进度。
5. 浏览器访问 `/api/files/direct-download?token=...` 时：
   - 后端对 token 进行签名校验、过期校验以及单次使用校验；
   - 校验通过后，重用现有 `buildDownloadResponse(...)` 方法流式返回文件内容；
   - 浏览器处理下载，用户获得完整文件。

### 3.2 下载 Token 设计

#### 3.2.1 Token payload 内容

建议的 payload 字段如下（JSON 格式）：

```json
{
  "fileId": 123,
  "userId": 456,
  "scope": "download",
  "nonce": "随机字符串",
  "exp": 1732081234
}
```

- `fileId`：文件 ID；
- `userId`：请求下载链接的用户 ID，用于权限校验和审计；
- `scope`：用途标记，当前为 `"download"`，为未来扩展保留空间；
- `nonce`：随机数，用于防止 token 在语义上重复，有利于实现“单次使用”；
- `exp`：过期时间戳（秒级或毫秒级）；按需求设置为**当前时间 +10 秒**。

#### 3.2.2 Token 结构与签名

- 使用 HMAC-SHA256：
  - `payloadJson` → `payloadBase64 = base64url(payloadJson)`；
  - `signature = HMAC-SHA256(payloadBase64, secret)`；
  - `token = payloadBase64 + "." + base64url(signature)`。
- 后端配置专用密钥与 TTL：

```yaml
download:
  token:
    secret: "一段不少于32字节的高强度随机密钥"
    ttl-seconds: 10
```

#### 3.2.3 Token 验证逻辑

在 direct-download 入口处（伪代码）：

1. 检查 `token` 是否存在；
2. 拆分为 `payloadBase64` 与 `signatureBase64`；
3. 重新计算 `HMAC-SHA256(payloadBase64, secret)` 与传入签名做常量时间比较；
4. 解析 payload：
   - 检查 `exp` 是否大于当前时间（可加 1–2 秒的安全裕量）；
   - 检查 `fileId`、`userId`、`scope`、`nonce` 格式是否正确；
5. 进入单次使用校验逻辑（见 3.3）。

### 3.3 “10 秒有效 + 单次使用”的具体实现

#### 3.3.1 时间限制（10 秒 TTL）

- Token 生成时：
  - `exp = now + ttlSeconds`，其中 `ttlSeconds = 10`；
  - 保证“下载链接生成后 10 秒内必须发起下载请求”，否则 token 过期。
- Token 使用时：
  - 在 direct-download 中读取 payload 中的 `exp`；
  - 若当前时间 `now > exp`，则返回 410 Gone / 401/403，提示“下载链接已过期，请重新发起下载”。

注意：这里限制的是“发起下载请求的时间”，不是要求整个下载过程在 10 秒内完成。浏览器只要在 10 秒内发出请求，后续下载可以持续更长时间。

#### 3.3.2 单次使用限制（只能成功下载一次）

为防止 token 被重复使用或被攻击者重放，需要保证“只要有一次下载真正开始，该 token 即被标记为已使用”。推荐实现方式如下：

- 新建一张“已使用下载 token”表：

```sql
CREATE TABLE download_tokens_used (
  token_hash VARCHAR(128) PRIMARY KEY,
  used_at TIMESTAMP NOT NULL
);
```

- 不直接存明文 token，而是存 `tokenHash = SHA-256(token)`，降低数据库泄露风险。

- 在 direct-download 逻辑中：

  1. 对 token 完成签名与 exp 校验；
  2. 计算 `tokenHash = SHA-256(token)`；
  3. 尝试执行插入：
     ```sql
     INSERT INTO download_tokens_used (token_hash, used_at)
     VALUES (:tokenHash, NOW());
     ```
  4. 若插入成功：说明该 token 首次使用 → 允许进入下载逻辑；
  5. 若触发主键冲突：说明该 token 已经被记录为“已使用” → 拒绝本次下载（返回 410 / 403），提示“下载链接已失效，请重新发起下载”。

- 清理策略：
  - 可按周期（例如每日）清理 `used_at` 早于某个时间点（如 7 天前）的记录；
  - 由于 token TTL 很短，表不会无限增大，配合定期清理即可长期稳定。

### 3.4 direct-download 接口设计

#### 3.4.1 路由与安全配置

- 新增接口：
  - `GET /api/files/direct-download?token=...`
- Security 配置：
  - 在 `SecurityConfig` 中配置该路径 `permitAll`，不再依赖 JWT Header；
  - 该接口仅依靠下载 token 进行安全校验。

#### 3.4.2 权限与用户状态再校验

在 direct-download 内部，除 token 验证外，还需进行权限与状态校验：

1. 通过 token payload 获取 `userId` 与 `fileId`；
2. 查询用户状态：
   - 用户是否存在；
   - 是否被禁用（enabled=false）；
   - 是否被锁定（locked=true）；
3. 调用 `fileService.getFileForDownload(fileId, userId)`：
   - 再次校验该用户对该文件的下载权限；
   - 防止“生成 token 后用户被禁用 / 文件被撤销权限”的情况。

只有当：

- token 验证通过（签名正确、未过期）；
- token 未被使用过（单次使用校验通过）；
- 用户处于有效状态；
- 文件仍然存在且用户具有下载权限；

时，才允许进入实际下载逻辑。

#### 3.4.3 实际下载逻辑

- 获取到 `File fileMeta` 与 `Path filePath` 后，复用现有的：
  - `buildDownloadResponse(request, fileMeta, filePath)` 方法；
  - 保留 Range、ETag、If-Modified-Since 等所有现有行为；
  - 使用 `StreamingResponseBody` + `FileChannel.transferTo` 流式输出文件。

- 审计与日志：
  - 推荐将 `buildDownloadResponse` 或外围调用处扩展一个可选参数 `Long userIdFromToken`；
  - 若通过 direct-download 入口触发下载，则审计记录使用 token 中的 userId，而非 SecurityContext（该接口不走 JWT）；
  - 避免日志中打印明文 token，可记录 `tokenHash` 或“通过 download-url 生成”之类的元信息。

### 3.5 前端改造方案

#### 3.5.1 新增获取下载 URL 的 API

在 `frontend/src/api/file.js` 中新增：

```js
import request from '@/utils/request'

export function getDownloadUrl(id) {
  return request({
    url: `/files/${id}/download-url`,
    method: 'get'
  })
}

export function getAdminDownloadUrl(id) {
  return request({
    url: `/files/admin/${id}/download-url`,
    method: 'get'
  })
}
```

说明：

- 这两个接口走现有 Axios 实例及 JWT 拦截器；
- 响应中包含 `url` 字段（例如 `/api/files/direct-download?token=...`）和 `expiresAt` 时间戳。

#### 3.5.2 各页面下载按钮逻辑调整

1. 用户文件列表页（`frontend/src/views/files/List.vue`）：

```js
import { getDownloadUrl } from '@/api/file'

const downloadFile = async (file) => {
  try {
    const res = await getDownloadUrl(file.id)
    const url = res.url
    if (!url) throw new Error('下载链接为空')
    window.open(url, '_blank')
  } catch (e) {
    console.error('获取下载链接失败:', e)
    ElMessage.error('获取下载链接失败，请稍后重试')
  }
}
```

2. 首页“最近文件”（`frontend/src/views/Home.vue`）：

#### 3.5.3 用户体验说明

- 用户每点击一次“下载”按钮，前端都会：
  1) 向后端请求一个**全新的**下载链接；
  2) 浏览器用该链接启动一个新下载任务（显示原生进度条）。
- 若下载过程中网络中断或用户取消：
  - 当前 token 已经被标记“已使用”，无法再次使用；
  - 用户只需再次点击“下载”按钮，即可获取新的 token 并重新发起下载。

### 3.6 安全性分析摘要

1. **时间窗口限制（10 秒 TTL）**：
   - 大幅降低 token 被窃取后被利用的概率；
   - 即使攻击者截获 token，也必须在 10 秒内抢先请求，否则 token 失效。

2. **单次使用保证**：
   - 通过数据库唯一主键插入策略，确保每个 token 只会成功用于一次下载；
   - 防止被重复分享或被脚本并发重放。

3. **权限与用户状态双重校验**：
   - 获取 download-url 时校验一次；
   - direct-download 时再校验一次；
   - 确保用户被禁用或文件权限变化后，旧 token 立即失效。

4. **日志与 Referer 风险控制**：
   - 后端日志不应打印完整 token，可记录 hash 或截断信息；
   - 建议对 direct-download 设置合适的 `Referrer-Policy`，避免 token 随 Referer 泄露给第三方；
   - 整个站点应强制使用 HTTPS，避免链路层窃听。

5. **XSS 风险说明**：
   - 若存在 XSS，恶意脚本可以窃取页面中的 token 或下载 URL；
   - 但 token 有 10 秒 TTL 且仅能使用一次，其价值低于长期 JWT；
   - 根本防线仍是避免 XSS，本方案在此基础上使下载链接的敏感度更可控。
