# 文件管理（新版）上传功能升级设计（2025-11-20 18:58）

## 一、背景与目标

### 1.1 背景

当前系统已经实现：

- 文件/文件夹统一管理的“文件管理（新版）”界面（Explorer），支持在同一列表中浏览当前目录下的文件夹与文件；
- 后端已经具备较完整的上传能力（直传、小文件上传、分片上传、断点续传、同用户秒传），并有《上传与分片/秒传接口说明（2025-11-17）》作为接口基础；
- 系统设置中提供了“上传策略”配置（白名单后缀、是否允许所有后缀等），以及“预览策略”，并已接入权限与审计逻辑。

但目前“文件管理（新版）”中的上传能力仍然偏简单/割裂：

- 上传入口仍偏向旧页面或简单接口，未与“当前目录”（folderId）深度绑定；
- 上传前后端仍有部分能力未完全打通（例如：前端未完整利用秒传/分片能力、断点续传体验一般）；
- 上传失败/网络波动等异常场景的处理较弱，缺乏统一的队列管理和重试策略。

### 1.2 目标

本设计的目标是：

1. 在“文件管理（新版）”中，构建一套**完备、健壮的上传子系统**，满足：
   - 多文件上传、拖拽上传；
   - 秒传（哈希去重）、直传与分片上传自动选择；
   - 大文件断点续传、失败重试；
   - 上传到**当前目录**（folderId 绑定），与“位置/路径”一致。
2. 严格对齐后端上传策略与权限：
   - 尊重“上传策略”白名单与最大大小限制；
   - 在有配额/权限限制时给出清晰可理解的错误提示；
   - 上传过程全程可审计。
3. 提供清晰的前端架构：
   - 通过组合式 API（composables）实现上传队列管理；
   - 将上传逻辑从具体页面中抽离，便于未来在其他页面复用。
4. 为后续扩展（如病毒扫描、业务流程审批、归档策略）预留挂载点。

不考虑时间成本与现阶段生产压力，追求设计完整、扩展性好、健壮性高。

## 二、整体架构与模块划分

### 2.1 前端总体结构

前端 Vue（3.x + composition API）中，引入以下模块：

1. 页面组件：
   - `frontend/src/views/files/Explorer.vue`  
     新版文件管理主界面，负责：
     - 显示目录树/面包屑；
     - 显示当前目录的文件夹与文件；
     - 承载上传入口（按钮、小拖拽区）；
     - 显示上传队列面板（底部抽屉/右侧面板）。

2. 上传队列组合函数（核心）：
   - 建议新建：`frontend/src/composables/useUploadQueue.js`（或 `useUploadQueue.ts`）  
     负责：
     - 管理上传任务列表（队列）；
     - 调度直传 / 秒传 / 分片上传；
     - 管理重试、暂停、恢复逻辑；
     - 对外暴露统一 API 供各页面使用。

3. 上传服务层：
   - 建议新建：`frontend/src/services/uploadService.js`  
     职责：
     - 封装对后端上传相关接口的调用（直传、秒传、分片上传、分片查询、合并等）；
     - 与 `src/api/file.js` 等接口模块解耦，避免组件直接操作过多 API。

4. 通用工具：
   - 文件哈希计算工具：`frontend/src/utils/fileHash.js`  
     - 使用 Web Crypto API（`crypto.subtle.digest`）在前端计算 SHA-256；
     - 对大文件采用分块流式哈希，以避免阻塞主线程。
   - 进度与时间格式化工具：复用现有 `formatFileSize`、`formatDateTime` 等工具，必要时抽到通用模块。

5. 配置与常量：
   - 上传相关常量配置：`frontend/src/config/upload.js`  
     包含：
     - 分片阈值（例如 10MB）；
     - 分片大小（例如 4MB）；
     - 单文件最大并发分片数（例如 3）；
     - 全局同时上传的文件数（例如 2–3）；
     - 分片重试次数（例如 3）。

### 2.2 后端接口依赖

后端接口继续沿用《上传与分片/秒传接口说明_20251117-1707》，在此基础上**补充 `folderId` 参数**和部分行为约束：

1. 直传：
   - URL：`POST /api/files/upload`
   - form-data 字段：
     - `file`: 必填，文件内容；
     - `folderId`: 可空/必填（视后端策略），代表目标目录；
     - `filename`: 可选，若未提供则从 file 中读取。

2. 秒传检查：
   - URL：`POST /api/files/fast-upload/check`
   - 请求体：
     - `hash`: 文件 SHA-256；
     - `size`: 文件大小；
     - `folderId`: 目标目录；
   - 响应：
     - `{ exists: true, fileId: xxx }` 或 `{ exists: false }`。

3. 分片上传：
   - URL：`POST /api/files/chunk`
   - form-data：
     - `chunk`: 当前分片；
     - `hash`: 整文件 SHA-256；
     - `index`: 分片序号（从 1 开始）；
     - `total`: 总分片数；
     - `folderId`: 目标目录；
   - 响应：
     - `{ ok: true }` 或带错误信息。

4. 分片状态查询：
   - URL：`GET /api/files/chunk/status?hash=...&total=...`
   - 响应：
     - `{ uploadedIndexes: [1,2,5] }` 等，便于前端补传缺片。

5. 合并分片：
   - URL：`POST /api/files/chunk/merge`
   - 请求体：
     - `hash`: 整文件 SHA-256；
     - `total`: 总分片数；
     - `filename`: 原始文件名；
     - `folderId`: 目标目录；
   - 成功响应：
     - `{ fileId: xxx, ... }`。

上述接口改动与细节在本设计中只作为前端的约束前提，本文件的重点在于前端如何正确调用与编排这些接口。

## 三、上传队列模块设计（useUploadQueue）

### 3.1 数据结构

在 `useUploadQueue` 中定义上传任务类型 `UploadTask`：

```ts
type UploadStatus =
  | 'pending'        // 已加入队列，尚未开始处理
  | 'hashing'        // 计算 SHA-256 中
  | 'checking_fast'  // 秒传检查中
  | 'waiting'        // 已准备好上传，等待调度
  | 'uploading'      // 正在上传（直传或分片）
  | 'merging'        // 分片合并中
  | 'completed'      // 成功完成
  | 'failed'         // 失败
  | 'paused'         // 暂停
  | 'canceled';      // 已被取消

interface UploadChunkState {
  index: number;       // 分片序号（1 开始）
  size: number;        // 分片大小
  uploaded: boolean;   // 是否已上传成功
  uploading: boolean;  // 当前是否正在上传
  retryCount: number;  // 已重试次数
  errorMessage?: string;
}

interface UploadTask {
  id: string;                // 前端生成 uuid
  file: File;                // 原生 File 对象
  name: string;              // 文件名
  size: number;              // 文件大小
  folderId: string | null;   // 目标文件夹
  hash: string | null;       // SHA-256（小写十六进制）
  status: UploadStatus;      // 当前状态
  progress: number;          // 0-100，总体进度
  uploadedBytes: number;     // 已上传字节数（便于计算进度）
  errorMessage?: string;     // 失败说明
  isFastUploaded: boolean;   // 是否通过秒传完成
  useChunks: boolean;        // 是否采用分片上传
  totalChunks?: number;      // 总分片数
  chunks?: UploadChunkState[]; // 分片状态数组
  createdAt: number;         // 入队时间戳
  updatedAt: number;         // 最近状态更新时间
}
```

在组合函数中维护：

```ts
const uploadQueue = ref<UploadTask[]>([])
const activeUploadsCount = ref(0) // 当前正在上传的文件数
```

并提供一组计算属性：

- `pendingTasks`、`runningTasks`、`failedTasks`、`completedTasks` 等；
- `hasRunningTasks`、`hasFailedTasks` 等布尔值，驱动 UI 展示状态。

### 3.2 对外 API 设计

`useUploadQueue` 对外暴露以下函数：

```ts
function enqueueFiles(files: File[], folderId: string | null): void
function startAll(): void
function pauseAll(): void
function cancelAll(): void

function pauseTask(taskId: string): void
function resumeTask(taskId: string): void
function cancelTask(taskId: string): void
function retryTask(taskId: string): void

// 供页面绑定
const uploadQueue = ref<UploadTask[]>
const hasRunningTasks = computed(...)
const stats = computed(() => ({ total, running, completed, failed }))
```

使用者（例如 `Explorer.vue`）只需要关心：

- 把用户选择的 `File[]` + 当前 `folderId` 传给 `enqueueFiles`；
- 通过 `uploadQueue` 显示进度和状态；
- 在用户操作时调用 `pauseTask`/`resumeTask` 等。

内部调度逻辑完全隐藏。

### 3.3 状态机与流程控制

#### 3.3.1 整体调度流程

1. `enqueueFiles(files, folderId)`：
   - 对每个文件创建 `UploadTask`，初始状态：
     - `status = 'pending'`；
     - `hash = null`；
     - `useChunks` 根据 size 与配置阈值预判（> 阈值则 true）；
     - `isFastUploaded = false`。
   - 将任务加入 `uploadQueue` 后，调用内部方法 `schedule()`。

2. `schedule()`：
   - 控制**同时上传的文件数**不超过 `maxConcurrentFiles`；
   - 扫描 `uploadQueue` 中状态为 `pending` / `waiting` / `paused`（但用户未手动暂停）的任务：
     - 优先处理 `pending` → 进入 `hashing`；
     - 已有 hash/检查完秒传的任务状态为 `waiting`，如果全局并发未超限，则进入 `uploading`。

3. `流程分支`：
   - 对于每个任务，前期流程统一为：
     1. `hashing`：计算 hash；
     2. `checking_fast`：调用秒传接口；
     3. 若 `exists=true` → 标记 `isFastUploaded=true`，直接 `completed`；
     4. 否则进入 `uploading`，根据 `useChunks` 选择直传或分片。

4. 任务结束：
   - `completed` 或 `failed` 后，将 `activeUploadsCount--`，并调用 `schedule()` 继续处理队列中其他任务。

#### 3.3.2 hash 计算（hashing）

实现要点：

- 使用 Web Crypto API：
  - 对小文件（例如 < 50MB），可以一次性读入（File.arrayBuffer）；
  - 对大文件，采用分块读取（File.slice + FileReader/ReadableStream），逐块 `crypto.subtle.digest`（或在内存内拼接处理，需注意性能）。
- 计算过程中，更新任务状态：
  - `status = 'hashing'`，可显示“计算哈希 xx%”（按读取的 bytes / 文件总大小估算）。
- 完成后：
  - 将 hash 写入 `task.hash`；
  - `status = 'checking_fast'`，进入秒传检查。

#### 3.3.3 秒传检查（checking_fast）

逻辑：

1. 调用 `uploadService.checkFastUpload({ hash, size, folderId })`；
2. 若 `exists === true`：
   - 调用后端创建引用的接口（若后端需要单独接口；或 seconds-check 本身即完成此事）；
   - `task.isFastUploaded = true`；
   - 状态 → `completed`；
   - 进度直接置为 100%，`uploadedBytes = size`；
   - 调用 Explorer 的“刷新当前目录”函数。
3. 若 `exists === false`：
   - 若 `task.useChunks === false`：
     - 状态 → `'waiting'`，由 `schedule()` 决定何时开始直传；
   - 若 `useChunks === true`：
     - 初始化 `chunks` 数组；
     - 可以再调用“分片状态查询”，填充已上传分片（断点续传场景）；
     - 状态 → `'waiting'`。

#### 3.3.4 直传（uploading, useChunks=false）

流程：

1. 状态置为 `uploading`；
2. 调用 `uploadService.directUpload(task, onProgress)`：
   - 内部使用 Axios 或原生 XHR 发起 multipart/form-data；
   - 通过 `onUploadProgress` 持续更新进度：
     - `task.uploadedBytes = loaded`；
     - `task.progress = Math.round(loaded / size * 100)`；
3. 成功：
   - 状态 → `completed`；
   - 进度 = 100，触发目录刷新。
4. 失败：
   - 根据错误类型判断是否自动重试：
     - 策略拒绝 / 413 / 权限不足：直接 `failed`，提示明确错误；
     - 网络超时 / 5xx：可有一层自动重试（文件级别重试次数可配置），重试完仍失败则标记 `failed`；
   - 将错误信息写入 `task.errorMessage`，供 UI 展示。

#### 3.3.5 分片上传（uploading, useChunks=true）

分片调度思路：

1. 初始化 `chunks`：
   - `totalChunks = Math.ceil(size / chunkSize)`；
   - 对每个分片构建 `UploadChunkState`，默认 `uploaded=false, uploading=false, retryCount=0`。
2. 若启用断点续传：
   - 调用 `uploadService.getChunkStatus(hash, totalChunks)`；
   - 根据返回的 `uploadedIndexes`，将对应分片标记为 `uploaded=true`，并累计 `uploadedBytes`。
3. 进入上传：
   - 状态 → `uploading`；
   - 启动一个内部循环/调度器 `uploadNextChunks(task)`：
     - 在每次调度中：
       - 统计当前 `chunks` 中 `uploading=true` 的数量，若 < `maxChunkConcurrencyPerFile`：
         - 找到尚未上传且未在上传中的分片；
         - 对该分片调用 `uploadService.uploadChunk(task, chunkState)`；
       - 每个分片上传成功：
         - `chunk.uploaded = true`、`uploading=false`；
         - `task.uploadedBytes += chunk.size`；
         - 根据 `uploadedBytes / size` 更新 `task.progress`；
       - 若分片失败：
         - 若 `retryCount < maxRetriesPerChunk`：延迟一小段时间重新调度该分片；
         - 否则：标记任务整体为 `failed`，停止调度。
   - 当所有分片 `uploaded=true`：
     - 状态 → `merging`；
     - 调用 `uploadService.mergeChunks(task)`；成功后状态 → `completed`。

暂停/恢复：

- 暂停任务：
  - 将 `task.status = 'paused'`；
  - 阻止调度器再启动新的分片上传；
  - 不刻意 cancel 已在途的请求（避免复杂度），但不再继续后续分片；
  - UI 显示为“已暂停”。
- 恢复任务：
  - `task.status = 'waiting'`；
  - 调用 `schedule()`，重新进入分片调度（只补传未完成分片）。

取消任务：

- 将 `status = 'canceled'`；
- 可选：若后端支持“清理未合并分片”的接口，前端可在取消时调用；
- 不再继续上传；UI 将该任务移入“已取消”区域（或允许从队列中移除）。

## 五、错误处理、权限与安全

### 5.1 错误类型分类

统一将后端错误归类：

1. 策略错误（上传策略/后缀白名单）：
   - HTTP 400/422，错误消息包含“后缀不允许”；
   - 前端提示：“上传策略不允许该文件类型，请联系管理员或在系统设置中调整上传策略。”；
   - 不自动重试。

2. 配额错误：
   - HTTP 413（Payload Too Large）或业务错误码；
   - 提示：“存储配额不足，请联系管理员或清理空间后重试。”；
   - 不自动重试。

3. 权限错误：
   - HTTP 403；
   - 提示：“没有上传到当前目录的权限，请联系管理员。”；
   - 不自动重试。

4. 网络错误/超时：
   - Axios `ECONNABORTED` 或无响应；
   - 提示：“网络异常，正在自动重试（x/3）…”；
   - 在分片层面进行有限次自动重试。

5. 服务器内部错误：
   - HTTP 500+；
   - 提示：“服务器异常，请稍后重试。如持续失败请联系运维。”；
   - 可按情况决定是否重试一次。

### 5.2 权限校验与 folderId 可信度

前端只负责传递当前 `folderId`，真正的权限校验位于后端：

- 任意上传请求必须带 token/会话信息，由后端识别用户；
- 后端根据用户与目录的 ACL 判定是否允许上传；
- 前端不尝试“自我屏蔽”目录，而是以后端返回结果为准。

### 5.3 安全性与 XSS/文件名处理

- 在前端显示文件名时，使用 Vue 默认的插值（自动 escape），避免 XSS；
- 后端在保存文件名时，需要做：
  - 去除控制字符；
  - 限制长度（例如 255 字节内）；
  - 对非常规字符做归一化（如 NFC）。

## 六、性能与配置

### 6.1 配置项建议

在 `upload.js` 中定义：

- `MAX_CONCURRENT_FILES = 2`；
- `MAX_CHUNK_CONCURRENCY_PER_FILE = 3`；
- `CHUNK_SIZE = 4 * 1024 * 1024`；
- `CHUNK_RETRY_LIMIT = 3`；
- `HASH_LARGE_FILE_THRESHOLD = 50 * 1024 * 1024`；
- `CHUNK_UPLOAD_TIMEOUT = 300000`（5 分钟）。

这些配置应支持未来通过环境变量或系统设置调整。

### 6.2 性能考虑

- 在 hash 大文件时，使用分块读取，避免一次性占用过多内存导致浏览器卡顿；
- 对于非常大的文件（例如 > 2GB），可考虑提示用户“上传时间较长，请保持页面打开”，未来可扩展为后台任务上传（本设计不展开）。

## 七、可观测性与审计

## 八、渐进式落地计划与风险

### 8.1 落地步骤

1. 先实现 `useUploadQueue` 基础版本：
   - 支持直传 + 秒传；
   - 队列管理/进度展示；
   - 接入 Explorer 的“上传按钮 + 队列面板”。
2. 在此基础上扩展分片上传：
   - 新增大文件分片逻辑；
   - 接入断点续传；
   - 增加错误重试。
3. 完善错误提示、队列操作（暂停/恢复/取消）和拖拽上传。
4. 在测试环境进行大文件压测与异常场景演练（网络中断、服务器重启等）。
5. 验证稳定后，评估是否将旧上传入口统一迁移到新版上传队列。

### 8.2 风险点与回滚策略

- 风险：新上传逻辑可能在极端网络/大文件场景下暴露 bug。
  - 策略：保留旧上传路径作为“兜底通道”，必要时可临时引导用户通过旧入口上传。
- 风险：前后端接口版本不一致导致上传失败。
  - 策略：在前端加入接口版本检查/探测逻辑，若发现后端未提供新接口，则自动退回旧上传方式。
