# 跨用户去重与文件版本历史设计（CAS + Versioning）

## 1. 目标与范围
- 跨用户物理去重：任意两个用户上传相同内容（SHA‑256 相同），仅保存一份物理文件（Blob）。
- 文件版本历史：单个用户下的单个文件保留多版本，可回档到任意历史版本。
- 兼容现有 API：在不破坏现有上传/下载/回收站语义下，增量扩展接口与数据结构。

## 2. 总体方案概述
- 引入内容寻址存储（Content‑Addressable Storage, CAS）：以文件内容 SHA‑256 作为唯一标识，集中落盘到 `blobs/` 目录；数据库新增 `blobs` 表做元数据管理与引用关系的锚点。
- 引入“用户文件（UserFile）+ 版本（FileVersion）”双层模型：用户的文件（在文件夹中的实体）有一条“当前激活版本”指针，历史版本记录在版本表中，每个版本指向一个 Blob。
- 现有 `File` 实体转为用户侧文件（或新建 `UserFile` 实体并迁移），其 `file_path/file_hash` 字段逐步废弃，由 `activeVersion.blob` 提供真实路径与哈希。

## 3. 数据模型（DDL 草案）
> 最终以 MySQL 8 为目标方言；以下仅供参考，落地时按实体注解/迁移脚本实现

- blobs（集中内容表，按 Hash 唯一）
  - hash VARCHAR(64) PRIMARY KEY  — SHA‑256 小写十六进制
  - size BIGINT NOT NULL
  - content_type VARCHAR(255)
  - path VARCHAR(1024) NOT NULL   — 物理存储路径（分层目录）
  - thumbnail_path VARCHAR(1024)  — 缩略图（可选）
  - created_at DATETIME NOT NULL
  - last_access_at DATETIME NULL  — 最近访问/下载时间（用于分层/归档）

- user_files（用户文件，原 `files` 语义）
  - id BIGINT PRIMARY KEY AUTO_INCREMENT
  - user_id BIGINT NOT NULL
  - folder_id BIGINT NULL
  - name VARCHAR(255) NOT NULL         — 原 `originalFilename`
  - active_version_id BIGINT NULL      — 指向 file_versions.id
  - deleted BOOLEAN NOT NULL DEFAULT 0
  - owner_hidden BOOLEAN NOT NULL DEFAULT 0
  - admin_delete_scheduled BOOLEAN NOT NULL DEFAULT 0
  - admin_delete_request_time DATETIME NULL
  - admin_delete_execute_time DATETIME NULL
  - admin_delete_reason VARCHAR(500) NULL
  - quota_released BOOLEAN NOT NULL DEFAULT 0
  - download_count INT NOT NULL DEFAULT 0
  - description TEXT NULL
  - create_time DATETIME NOT NULL
  - update_time DATETIME NOT NULL
  - delete_time DATETIME NULL
  - 索引：idx_user_folder(user_id, folder_id, deleted), idx_name(name)

- file_versions（版本记录）
  - id BIGINT PRIMARY KEY AUTO_INCREMENT
  - file_id BIGINT NOT NULL            — FK → user_files.id
  - version_no INT NOT NULL            — 从 1 递增，(file_id, version_no) 唯一
  - blob_hash VARCHAR(64) NOT NULL     — FK → blobs.hash
  - size BIGINT NOT NULL
  - content_type VARCHAR(255)
  - comment VARCHAR(255) NULL          — 版本备注（回档/重命名说明）
  - created_by BIGINT NOT NULL         — 用户 id
  - create_time DATETIME NOT NULL
  - 约束：UNIQUE(file_id, version_no)

> 说明：为降低改造面，可先保留 `files` 表，增列 `active_version_id` 并将其语义转为 `user_files`，逐步迁移；或并行新表后以任务迁移并替换读路径。

## 4. 存储路径规范
- Blob 路径：`{storageRoot}/blobs/{h0}{h1}/{h2}{h3}/{hash}`（按前 4 位散列分层）
- 缩略图路径：`{storageRoot}/thumbs/{h0}{h1}/{h2}{h3}/{hash}.jpg`
- 临时上传目录：`{storageRoot}/tmp/{uuid}`（实际写入时流式计算哈希）

## 5. 服务与仓库改造
- 新增实体/仓库
  - Blob（blobs）、BlobRepository
  - FileVersion（file_versions）、FileVersionRepository
  - 将现 `File` 重命名为 `UserFile`（或过渡期并存）：更新 repository 查询域。

- 新增服务
  - BlobService：
    - 接口：`find(hash) / exists(hash) / createFromTemp(tmpPath, hash, size, contentType)`
    - 写路径采用“临时 → 原子移动”的并发安全策略；如并发创建以 CREATE_NEW 失败则转为使用已存在 Blob。
    - 首次需要时生成缩略图（同样用文件锁/DB 乐观并发控制确保只生成一次）。
  - VersionService：
    - `createFirstVersion(userFile, blobHash, meta)`、`createNewVersion(userFile, blobHash, comment)`、`list(fileId)`、`revert(fileId, versionNo)`

- 重构 FileService（关键流程）
  - 上传（单体与分片合并）：
    1) 流式写入临时文件并计算 SHA‑256、统计 size/contentType。
    2) 若 `Blob.exists(hash)`：丢弃临时文件 → 创建/更新 `user_files` 与 `file_versions`（跨用户秒传）。
    3) 否则：原子移动临时文件至 Blob 路径 → 新建 Blob 行 → 建版本。
    4) 配额调整（见下）。
  - 下载：通过 `user_files.active_version.blob.path` 读取，ETag 使用 `blob.hash`，保留 Range/If‑Range/304 逻辑。
  - 删除：
    - 软删：只标记 `user_files.deleted=true`；
    - 彻删：删除该文件所有版本记录；若某 Blob 无任何版本引用，则删除物理文件和 `blobs` 行（GC 亦可异步做）。

## 6. API 设计（在现有基础上增量）
- 兼容：
  - `POST /api/files/upload`：新增 `parentId`（可选，指定为现有文件则创建新版本，否则创建新文件+v1）。
  - `POST /api/files/exists`：保留“用户内 exists”（兼容旧前端）。
- 新增：
  - `POST /api/files/exists-global`：body `{fileHash}` → `{exists, size, contentType}`（命中 Blob 即 true）。
  - `GET /api/files/{fileId}/versions`：列版本（`id/versionNo/hash/size/contentType/createTime/comment`）。
  - `POST /api/files/{fileId}/versions`：创建新版本（通过已有 `blobHash` 或上传）。
  - `POST /api/files/{fileId}/revert`：回档到 `versionNo`（实现为追加新版本指向历史 Blob，或切换激活指针；推荐前者）。
  - `GET /api/files/{fileId}/download?version=versionNo`：下载指定版本（默认当前版本）。

## 7. 配额策略（可配置，默认建议“仅计当前版本”）
- 仅计当前版本（建议）：
  - 创建新版本时配额增量 = `max(0, new.size - active.size)`；回档时按差值调整；彻删释放当前激活版本大小。
- 计全量历史版本：
  - 每新增版本占用完整 size；彻删释放所有版本大小。
- 字段沿用：`users.quotaUsed/quotaLimit` 与 `quota_released` 逻辑保留在 `user_files` 维度。

## 8. 并发与一致性
- Blob 写入采用“双检 + 原子移动（ATOMIC_MOVE + CREATE_NEW）”：
  - 若 `exists(hash)` 为假，尝试 `Files.move(tmp, blobPath, CREATE_NEW)`；失败则表示并发命中，转为使用现有 Blob。
- 分片合并时边合并边更新 digest，完成后对比前端传入 `fileHash` 校验一致。
- 缩略图生成使用基于文件系统的轻量锁或基于 DB 的互斥。

## 9. 垃圾回收（GC）
- 定时任务：
  - 查找未被引用的 Blob：`SELECT b.hash FROM blobs b LEFT JOIN file_versions v ON b.hash=v.blob_hash WHERE v.blob_hash IS NULL`；
  - 删除对应物理文件与 `blobs` 行；
  - 可结合 `last_access_at` 做分层或冷数据迁移。

## 10. 迁移计划
- 阶段 1（引入新表 + 新代码路径）
  - 建表：`blobs/user_files/file_versions`。
  - 上传/下载优先走新路径；旧 `files` 读取保留兼容（若 active_version 为空则回退旧字段）。
- 阶段 2（旧数据回填与去重）
  - 遍历 `files`，按 `file_hash` 分组；对每个 hash：
    - 若对应 Blob 不存在：将其中一份物理文件原子移动至 Blob 路径并建 Blob 行；
    - 其他同 hash 的物理副本删除（或替换为硬链接，视文件系统能力与部署约束）。
  - 为每条 `files` 生成 `user_files` 与 `file_versions`（version_no=1，blob_hash=原 hash），将 `active_version_id` 指向之。
- 阶段 3（切换与收尾）
  - 控制器下载仅走 Blob 路径；
  - 标记旧列废弃；
  - 启用 GC；
  - 前端接入版本列表/回档。

## 11. 代码改造指引（关键文件）
- 服务层：
  - 新增 `BlobService`、`VersionService`；
  - 重构 `FileService.uploadFile/mergeChunks`（backend/src/main/java/com/filemanager/service/FileService.java:65, 223）对接 Blob + Version；
  - 重构 `FileService.getFilePath/getFileForDownload` 使用 activeVersion.blob.path；
- 控制器：
  - `FileController` 下载路径改为通过版本解析 Blob；保留 Range/If‑Range/304/ETag（以 `blob.hash` 作为 ETag）。
  - 新增版本相关路由：`/exists-global`、`/versions`、`/revert`、`/download?version=`。
- 仓库与实体：
  - 新建 `BlobRepository`、`FileVersionRepository`；
  - 迁移 `File` → `UserFile`（或过渡期改语义并保留名称），新增 `activeVersionId` 及关联。

## 12. 风险与注意事项
- 大规模迁移时的 IO 峰值：建议分批/限速；
- 硬链接方案依赖底层文件系统与容器挂载参数，不做默认依赖；
- 配额口径变更需对齐产品期望并做数据迁移校验；
- 缩略图与预览文件需转移到 Blob 维度，避免重复生成与清理遗漏。

## 14. 验收要点
- 跨账号上传相同大文件，磁盘仅一份；两边均能正常下载，ETag 相同。
- 对同一用户同一文件多次上传生成版本（或通过回档生成版本），可在历史版本间切换/下载；
- 回收站彻删后，若无版本引用则物理文件被清理。
