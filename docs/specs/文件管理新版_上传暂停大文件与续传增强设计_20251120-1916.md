# 文件管理（新版）上传暂停、大文件哈希与页面刷新续传增强设计（2025-11-20 19:16）

## 一、设计范围与目标

围绕当前“文件管理（新版）”上传实现，补齐三个关键能力：

1. **上传任务暂停 / 恢复 / 取消的真实语义**  
   - 现在：仅修改前端状态，不真正中断网络请求和分片调度。  
   - 目标：实现“网络级中断 + 分片级停顿”，达到用户预期的暂停/取消效果。

2. **极大文件（单文件 4GB 级别）哈希计算能力**  
   - 现在：使用 Web Crypto + `file.arrayBuffer()` 一次性加载，4GB 场景下不可接受。  
   - 目标：提供流式/分块哈希方案，支持大文件且不阻塞 UI。

3. **页面刷新后的未完成任务恢复提示与续传能力**  
   - 现在：刷新页面队列即丢失，但服务器端已上传分片仍可利用（通过 `chunk/status`）。  
   - 目标：刷新后提示“有未完成任务”，用户可选择恢复，重新挂载文件后继续上传（尤其是分片续传）。

本设计只给出前端侧详细方案，不要求更改现有后端接口（后端已有分片与秒传能力即可支撑）。

## 二、暂停 / 恢复 / 取消的真实语义设计

### 2.1 现状问题与目标语义

现状（useUploadQueue）：

- `pauseTask`：仅将状态标记为 `paused`，调度器不再“新开任务”，但正在上传的分片会继续；  
- `resumeTask`：将状态改回 `pending`，允许重新调度；  
- `cancelTask`：仅从前端队列数组中移除任务，未真正通知服务端“终止上传”；
- 对直传任务 `uploadDirect` 和分片 `uploadByChunks`，内部循环不会根据 `task.status` 及时退出。

目标语义：

1. **暂停**：
   - 当前正在上传的分片 / 直传请求应尽快中断（可接受“下一个网络边界”结束）；
   - 不再上传新的分片；
   - 任务状态进入 `paused`，用户可恢复。
2. **恢复**：
   - 从任务当前进度继续：
     - 对直传：建议重走一次完整上传（因为中间状态不可恢复）；
     - 对分片：基于已上传分片清单补传剩余分片。
3. **取消**：
   - 尽快中断所有在途请求；
   - 不再继续该任务；
   - 队列中移除，后端已有分片视为“垃圾”，由服务端清理任务处理。

### 2.2 技术手段：请求取消与状态检查

1. **请求取消机制选择（Axios + 浏览器）**

在当前 axios 使用方式下，有两种实现路径：

- **方案 A：Axios CancelToken 或 `AbortController`（推荐）**
  - 为每个“请求”关联一个 `cancelToken` 或 `signal`；
  - 暂停/取消时调用对应的 `cancel()` / `abort()`，axios 会中断请求；
  - 需要在 `uploadService` 的 `directUpload` / `uploadChunk` 函数中接受 `cancelToken`/`signal` 参数。

- **方案 B：忽略网络中断，只在逻辑上中断调度（已部分实现）**
  - 不再新增请求，但已有请求会跑完；
  - 只能部分满足“暂停慢慢生效”的语义；
  - 体验相对差，本设计不作为目标方案。

本设计采用 **方案 A**，在 `useUploadQueue` 上维护一套“任务级取消控制器”。

2. **任务级取消控制器设计**

在队列中为每个任务增加：

```ts
interface UploadTask {
  // 现有字段...
  controllers?: {
    hashing?: AbortController;         // 可选：用于大文件哈希
    currentRequest?: AbortController;  // 当前直传或分片请求
  }
}
```

调整 uploadService 函数签名：

```js
export function directUpload({ file, folderId, filename, onUploadProgress, signal }) { ... }

export function uploadChunk({ hash, index, total, chunk, onUploadProgress, signal }) { ... }
```

在 useUploadQueue 内部：

- 每次发起直传或分片上传前创建新的 `AbortController`，保存到 `task.controllers.currentRequest`，并将 `signal` 传给 uploadService；
- 暂停/取消时，若 `task.controllers.currentRequest` 存在，则调用 `abort()` 中断请求；
- 请求完成/失败后，清空 `currentRequest` 引用，避免多次 abort。

3. **状态检查与循环中断**

在分片逻辑中：

```js
const runChunks = async () => {
  while (true) {
    if (task.status === 'paused' || task.status === 'canceled') break
    const pending = (task.chunks || []).filter(c => !c.uploaded && !c.uploading)
    if (!pending.length) break
    const batch = pending.slice(0, MAX_CHUNK_CONCURRENCY)
    await Promise.all(batch.map(c => doUploadChunk(c)))
  }
}
```

在 `doUploadChunk` 或 progress 回调中也应定期检查 `task.status` 是否已变为 `canceled`，若是则中断后续逻辑。

### 2.3 暂停 / 恢复 / 取消流程设计

1. **暂停流程**

```js
const pauseTask = (taskId) => {
  const task = findTask(taskId)
  if (!task) return
  if (['hashing','checking_fast','uploading','merging'].includes(task.status)) {
    // 标记状态
    updateTask(task, { status: 'paused' })
    // 中断当前请求
    if (task.controllers?.currentRequest) {
      task.controllers.currentRequest.abort()
    }
    if (task.controllers?.hashing) {
      task.controllers.hashing.abort()
    }
  }
}
```

暂停含义：

- 当前在途请求在 abort 后立即报错，由上传逻辑捕获并判断 `task.status === 'paused'` 时忽略错误（不标记为 failed）；
- 分片调度看到 `paused` 后不再开新分片请求。

2. **恢复流程**

恢复只恢复 `paused` 的任务：

```js
const resumeTask = (taskId) => {
  const task = findTask(taskId)
  if (!task) return
  if (task.status === 'paused') {
    // 将任务重新置为 pending，调度器会按当前进度继续上传
    updateTask(task, { status: 'pending' })
    schedule()
  }
}
```

对不同阶段：

- 对于直传任务：  
  - 暂停后无法恢复“半个 HTTP 请求”的状态，恢复时建议重新走一遍完整上传；  
  - 这在直觉上可以接受，因为直传往往文件较小。
- 对于分片任务：  
  - 因为已经记录了 `chunks.uploaded`，恢复时只需补上传剩余分片即可；  
  - `getChunkStatus` 也可以在恢复时再调用一次以同步服务器端状态。

3. **取消流程**

```js
const cancelTask = (taskId) => {
  const task = findTask(taskId)
  if (!task) return
  if (task.status === 'completed') return

  // 标记为 canceled，阻止后续逻辑
  updateTask(task, { status: 'canceled' })

  // 中断当前请求
  if (task.controllers?.currentRequest) {
    task.controllers.currentRequest.abort()
  }
  if (task.controllers?.hashing) {
    task.controllers.hashing.abort()
  }

  // 从队列移除
  removeTask(taskId)
}
```

注意：

- 服务端已有的分片数据不会立即清掉，本设计依赖后端的异步清理任务（或按需增加“清理分片”接口）。  
- 对于已完成的 merge，不允许“取消”，只允许从 UI 中隐藏任务（保持最终一致性）。

## 三、极大文件（4GB）哈希计算设计

### 3.1 问题分析

当前实现：

```js
const buffer = await file.arrayBuffer()
const hashBuffer = await crypto.subtle.digest('SHA-256', buffer)
```

问题：

- 对 4GB 文件，`arrayBuffer()` 会一次性占用 4GB 内存，不现实；
- 期间主线程可能大量阻塞，冻结 UI；
- 移动端或内存较小环境风险更大。

目标：

- 支持对 4GB 级别文件进行哈希；
- 不一次性分配巨大 ArrayBuffer；
- 尽可能不阻塞 UI，可以接受“略慢但稳定”的计算。

### 3.2 实现路径对比

**方案 A：前端引入可增量更新的 SHA-256 JS 实现（推荐）**

思路：

- 使用纯 JS 或 WebAssembly 实现的 SHA-256 库（例如 crypto-js、js-sha256 或引入已有的 incremental SHA-256 实现）；
- 支持典型接口： `hasher.update(chunk)`, `hasher.digest()`；
- 通过 `File.slice` + `FileReader.readAsArrayBuffer` 或 `ReadableStream` 逐块读取文件；  
- 在每块读取完成时调用 `hasher.update`，释放掉该块的内存；
- 计算完所有块后调用 `digest()` 得到哈希。

优点：

- 真正的流式，峰值内存仅为单块大小（例如 4MB）；
- 无需完全依赖 Web Crypto 不够灵活的接口；
- 易于与 AbortController 集成（随时 stop）。

缺点：

- 需要引入第三方库，稍微增加前端 bundle 体积；
- 性能略逊于原生 WebCrypto（但在 4GB 这样的大文件场景下，I/O 本身就是主要瓶颈）。

**方案 B：WebCrypto + Worker + 分块拼接（不推荐）**

理论上可以通过各种“重计算 + 部分 digest”组合方式实现，但 WebCrypto 对增量 digest 支持有限，容易引入 O(n²) 复杂度和实现复杂度，本设计不推荐。

### 3.3 推荐实现细节（方案 A）

1. 新增工具模块 `fileHashStreaming.js`：

```js
export async function computeFileSha256Streaming(file, options = {}) {
  const {
    chunkSize = 4 * 1024 * 1024,
    onProgress,
    signal
  } = options

  const hasher = new IncrementalSha256() // 来自第三方库
  const total = file.size
  let offset = 0

  while (offset < total) {
    if (signal?.aborted) throw new Error('hash_aborted')
    const end = Math.min(offset + chunkSize, total)
    const blob = file.slice(offset, end)
    const buf = await blob.arrayBuffer()
    hasher.update(new Uint8Array(buf))
    offset = end
    if (onProgress) onProgress(offset, total)
  }
  const hashHex = hasher.digest('hex')
  return hashHex
}
```

2. 与暂停/取消集成：

- `useUploadQueue` 在 `startTask` 里：
  - 为 hash 阶段创建 `hashingController = new AbortController()`；
  - 调用 `computeFileSha256Streaming(file, { signal: hashingController.signal, onProgress })`；
  - 暂停/取消时调用 `hashingController.abort()`；
  - 捕获 `hash_aborted` 时将任务状态保持为 `paused`，不标记为失败。

3. Worker 化（可选增强）：

- 将 `computeFileSha256Streaming` 放入 Web Worker，主线程通过 `postMessage` 发送 file + chunkSize + signalId；  
- Worker 逐块读取并计算哈希，通过 `postMessage` 回传 progress 与最终 hash；  
- 主线程负责 UI 更新与取消信号；
- 这样可以进一步避免哈希计算占用主线程时间。

## 四、页面刷新后的任务恢复与续传设计

### 4.1 制约与原则

重要约束：

- 浏览器刷新后，原来的 `File` 对象无法恢复，用户必须重新选择本地文件；  
- 服务器端已有的分片状态可以通过 `/chunk/status` 恢复；
- 我们只能在前端持久化“任务元数据”，不能持久化真正的文件内容。

设计原则：

1. 刷新后只恢复“任务描述 + 已上传进度”，需要用户重新选择文件来继续上传；
2. 对分片任务，尽可能利用已有分片，避免重复上传；
3. 界面上用明确文案解释这一行为，避免用户误解为“自动续传无需重新选文件”。

### 4.2 本地持久化结构设计

在 localStorage 中存储：

```ts
interface PersistedTask {
  id: string
  name: string
  size: number
  folderId: string | null
  hash: string | null
  useChunks: boolean
  createdAt: number
  lastStatus: string   // 'pending' | 'uploading' | 'paused' | 'failed' ...
}

interface PersistedState {
  version: 1
  tasks: PersistedTask[]
}
```

存储策略：

- 在 `useUploadQueue` 的 `updateTask` 中，每次状态变化后调用 `persist()`：  
  - 只持久化 `status` 属于 `pending / hashing / checking_fast / uploading / paused / failed` 的任务；  
  - 已 `completed` 的任务不再持久化。

### 4.3 刷新后的恢复流程

1. 页面加载时（Explorer mounted）：

```js
const persisted = loadPersistedUploadState()
if (persisted.tasks.length > 0) {
  // 弹出对话框：
  // “检测到上次会话中有未完成的上传任务，是否尝试恢复？”
}
```

2. 用户选择“恢复”：

- 将 `PersistedTask` 转换为 `UploadTask` 占位对象：  
  - `file` 字段暂设为 `null`；  
  - 状态设为 `paused`；  
  - 在队列 UI 中以灰色提示“待重新选文件”；  
  - 显示 hash（若已有）和大小，方便用户确认是哪一个文件。

3. 用户重新选择文件：

- 在上传队列抽屉中为“待恢复任务”提供一个“选择文件继续上传”按钮；  
- 点击后弹出 file picker，只允许选择单个文件；  
- 验证：  
  - 文件名必须与 `PersistedTask.name` 匹配（或给出“文件名不同”提示）；  
  - 文件大小必须与 `PersistedTask.size` 一致；  
- 验证通过后，将选中的 `File` 对象绑定到该任务的 `file` 字段：  
  - 若原来已有 `hash`，可以直接跳到分片阶段（调用 `getChunkStatus` 以利用已上传分片）；  
  - 若 `hash` 为空，则重新执行 hash + 秒传检查逻辑。

4. 用户也可以选择“放弃”：

- 清空本地持久化状态，不再提示恢复；
- 服务器端分片最终由清理任务处理。

### 4.4 与暂停/分片的协同

恢复后的分片任务流程：

1. 重新绑定 `File` 对象；
2. 若 `hash` 已知：
   - 直接进入 `uploadByChunks`；  
   - 由 `getChunkStatus` 获取服务器端已有分片；
3. 若 `hash` 未知：
   - 先使用流式哈希功能计算 hash（可复用已有 hash 结果）；
   - 再走秒传检查与分片上传。

这样可以在不存储文件内容的情况下利用已上传分片，减少重复上传成本。

## 五、实施建议与迭代顺序

建议按以下顺序逐步落地：

1. **第一阶段：请求取消 + 分片状态检查**  
   - 在 uploadService 中为所有上传请求加入 `AbortController`/`signal` 支持；  
   - 在 useUploadQueue 中为任务维护 `controllers`，实现“真实暂停/取消”；
   - 在分片调度循环中加 `task.status` 检查。

2. **第二阶段：流式哈希 + Worker（可选）**  
   - 引入增量 SHA-256 实现（JS 库或自研）和 `computeFileSha256Streaming`；  
   - 用 `AbortController` 与暂停/取消联动；  
   - 如有大文件上传需求明显，再考虑 Worker 化。

3. **第三阶段：本地持久化与恢复 UI**  
   - 在 useUploadQueue 中实现持久化/恢复逻辑；  
   - 在 Explorer 中增加启动弹窗以及“选择文件继续上传”的交互；  
   - 整体体验确认后再完善文案细节。

4. **第四阶段（可选）：后端清理策略与协同优化**  
   - 若大规模分片继续积累，可与后端约定清理策略或提供“主动清理分片”接口；  
   - 在前端取消任务时可选择调用该接口减少垃圾分片。

本设计为前端增强的详细方案，实际实现时应继续遵循当前项目文档与变更记录约定：  
每一阶段的代码改动前先在 `docs/changes` 下新增对应的变更设计与实施记录，并在 `docs/文档变更总记录.md` 中登记。
