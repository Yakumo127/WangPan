# 文件预览：PDF 浏览器原生预览方案（2025-11-20 16:40）

## 一、背景与现状

1. 预览接口后端现状
- 接口：`GET /api/files/{fileId}/preview`；
- 后端已经从 `StreamingResponseBody` 改为 `Resource + contentLength` 实现：
  - 认证与权限校验（普通用户 / 管理员）；
  - 预览后缀白名单校验；
  - 路径归属存储根目录校验；
  - 使用 `Files.size(filePath)` 设置 `Content-Length`；
  - 通过 `FileSystemResource` 返回文件内容；
  - `Content-Type` 按扩展名和文件信息计算（pdf/image/text 等）；
  - `Content-Disposition: inline; filename="..."`；
  - 保留审计日志（成功/失败）；
  - 已经解决“HTTP 200 但请求长期未完成”问题。

2. 前端预览现状
- 请求层：
  - `previewFile(id)` 使用 Axios：
    ```js
    return request({
      url: `/files/${id}/preview`,
      method: "get",
      responseType: "blob",
      timeout: 0
    })
    ```
  - `responseType === 'blob'` 时拦截器直接返回原始 `response`，前端拿到 `res.data` 作为 Blob。
- 预览页 `Preview.vue`：
  - 在 `onMounted` 中调用 `loadPreview()`：
    ```js
    const res = await previewFileApi(fileId.value)
    const blob = res?.data
    // 综合 headers['content-type'] + 扩展名判定 viewerType
    // viewerType === 'text' → blob.text()
    // viewerType === 'pdf' → blob.arrayBuffer() → Uint8Array 交给 PdfViewer 渲染
    // 其他类型 → URL.createObjectURL(blob) → blobUrl（用于 iframe 或 video）
    ```
  - 模板使用 `<PdfViewer :data="pdfData" />` 渲染 PDF，其他类型使用 `<video>` 或 `<iframe>`。

3. 当前 PDF 预览问题
- 控制台错误：
  ```text
  PDF 渲染失败: Error: Setting up fake worker failed:
  "Cannot load script at: https://unpkg.com/pdfjs-dist@3.11.174/build/pdf.worker.min.js"
  ```
- 原因：
  - `PdfViewer.vue` 中配置：
    ```js
    import * as pdfjsLib from 'pdfjs-dist/build/pdf'
    pdfjsLib.GlobalWorkerOptions.workerSrc = 'https://unpkg.com/pdfjs-dist@3.11.174/build/pdf.worker.min.js'
    ```
  - 在当前部署环境中，无法访问外网 CDN（unpkg），导致：
    - pdf.js 内部尝试加载 worker 脚本失败；
    - fake worker 也无法 setup 成功；
    - 整个 PDF 解析过程抛出异常；
    - 触发 Vue 渲染错误，导致页面出现额外的 `insertBefore` 相关报错。

结论：在当前网络环境下，**基于 pdf.js 的 PDF 渲染方案因外网 CDN 受限导致无法工作**。需要回到一条不依赖外网、尽量简单、且不再修改后端的方案。

## 二、目标与原则

1. 不再修改后端接口行为：
   - 保持 `GET /api/files/{id}/preview` 现有实现不变；
   - 继续依赖后端的权限校验、路径安全、Content-Type 与 Content-Length 设置。

2. 前端实现“PDF 浏览器原生预览”：
   - 前端只负责通过 Axios 拿到 Blob；
   - PDF 的实际渲染交给浏览器内置 PDF Viewer（或内置的 PDF 支持），通过 `<iframe src="blob:...">` 完成；
   - 不再依赖 pdf.js 的 worker 脚本，也不依赖任何外部 CDN。

3. 保持图片、视频、文本等其他类型预览的现有行为：
   - 图片仍由列表页对话框预览；
   - 文本仍使用 `<pre>` 显示；
   - 视频仍使用 `<video>` 播放；
   - Office 文档暂时交给浏览器/插件通过 `<iframe>` 尝试渲染，未来 doc/ppt → PDF 转换仍按“暂时搁置修复事项”处理。

## 三、技术思路：Blob + iframe 由浏览器原生渲染

### 1. 核心思路

1. 仍通过 Axios 获取预览文件 Blob：
   ```js
   const res = await previewFileApi(fileId.value)
   const blob = res?.data
   ```

2. 使用响应头 `Content-Type` + 扩展名判断内容类型：
   - 如果 `Content-Type` 包含 `application/pdf`，则视为 PDF；
   - 如果 `Content-Type` 以 `video/` 开头或扩展名为 `mp4`，视为视频；
   - 如果 `Content-Type` 以 `text/` 开头或扩展名在 `txt/log/md` 中，视为文本；
   - 否则视为“通用二进制”，交给浏览器/插件处理。

3. 对于 PDF / Office / 其他二进制类型：
   - 在前端直接生成一个 `blob:` URL：
     ```js
     const finalBlob = viewerType === 'pdf' && blob.type !== 'application/pdf'
       ? new Blob([blob], { type: 'application/pdf' })
       : blob
     const url = window.URL.createObjectURL(finalBlob)
     blobUrl.value = url
     ```
   - 在模板中统一使用 `<iframe :src="blobUrl" />` 进行预览；
   - 浏览器检测到 `Content-Type: application/pdf` 的 blob URL 时，优先使用内置 PDF Viewer 渲染；
   - 若浏览器不支持内置 PDF Viewer，则表现为触发下载或交由插件处理。

4. 对于视频：
   - 同样生成 blob URL；
   - 使用 `<video :src="blobUrl" controls>` 播放。

5. 对于文本：
   - 使用 `blob.text()` 读取文本内容；
   - 使用 `<pre>{{ textContent }}</pre>` 展示。

### 2. 与 pdf.js 方案的对比

1. 优点：
   - 不再依赖外网 CDN，不受 `pdf.worker.min.js` 无法加载影响；
   - 利用浏览器内置 PDF 支持，行为简单、易于理解；
   - 不需要引入 pdf.js 及其 worker 资源，减少前端包体和复杂度；
   - 与当前后端 `/preview` 接口完全兼容，不需要后端做任何额外改动。

2. 缺点：
   - 功能上受限于浏览器内置 PDF Viewer：
     - 缩放、查找、打印等能力取决于浏览器自身；
     - 无法在前端完全掌控渲染细节（例如分页、定制工具栏等）。
   - 在不支持 PDF 内联预览的浏览器中，可能表现为下载而非预览。

3. 适用场景：
   - 当前部署环境无法访问外部 CDN 或外网受限；
   - 对 PDF 预览的需求主要是“看内容”，不要求高度定制的交互；
   - 更关注稳定性和实现简单度。

## 四、具体前端改造方案

以 `frontend/src/views/files/Preview.vue` 为核心修改点，设计如下。

### 1. 状态与类型判定

- 保留已实现的基于响应头 + 扩展名的类型判定：

```js
const viewerType = ref('unknown')

const getExt = () => {
  const name = filename.value || ''
  const idx = name.lastIndexOf('.')
  if (idx < 0) return ''
  return name.slice(idx + 1).toLowerCase()
}

const loadPreview = async () => {
  const res = await previewFileApi(fileId.value)
  const blob = res?.data
  if (!(blob instanceof Blob)) throw new Error('预览数据无效')

  const ext = getExt()
  const contentType = (res && res.headers && (res.headers['content-type'] || res.headers['Content-Type'])) || ''

  let type = 'unknown'
  if (contentType && contentType.includes('application/pdf')) {
    type = 'pdf'
  } else if (contentType.startsWith('video/') || ext === 'mp4') {
    type = 'video'
  } else if (contentType.startsWith('text/') || ['txt', 'log', 'md'].includes(ext)) {
    type = 'text'
  } else if (['doc', 'docx', 'ppt', 'pptx'].includes(ext)) {
    type = 'office'
  }
  viewerType.value = type

  if (viewerType.value === 'text') {
    textContent.value = await blob.text()
  } else {
    // PDF、视频、Office、未知类型统一创建 blob URL
    let finalBlob = blob
    if (viewerType.value === 'pdf' && blob.type !== 'application/pdf') {
      finalBlob = new Blob([blob], { type: 'application/pdf' })
    }
    const url = window.URL.createObjectURL(finalBlob)
    blobUrl.value = url
  }
}
```

- 不再维护 `pdfData` 与 PdfViewer 组件引用。

### 2. 模板结构调整

模板统一为三种分支：

```vue
<template v-if="viewerType === 'video'">
  <video v-if="blobUrl" class="preview-video" controls :src="blobUrl"></video>
</template>
<template v-else-if="viewerType === 'text'">
  <pre class="preview-text">{{ textContent }}</pre>
</template>
<template v-else>
  <iframe v-if="blobUrl" :src="blobUrl" class="preview-iframe" />
</template>
```

- PDF、Office、其他二进制类型都进入 `else` 分支，由 `<iframe>` 统一展示；
- 不再使用 `<PdfViewer>` 组件，也不再依赖 pdf.js。

### 3. 清理与兼容

- 在 `Preview.vue` 中删除对 `PdfViewer` 的 `import` 和 `pdfData` 状态；
- 不删除 `PdfViewer.vue` 文件和 `pdfjs-dist` 依赖（保留为未来可能恢复 pdf.js 方案的基础）；
  - 当前代码不会再引用 `PdfViewer`，打包后不会引入 pdf.js 的运行时代码，也不会再尝试加载 `pdf.worker.min.js`。
- 图片预览逻辑仍然在 `List.vue` 中通过弹出图片对话框实现，不受本次修改影响。

## 五、后续优化与注意事项

1. 浏览器兼容性
- 主流桌面浏览器（Chrome/Edge/Firefox）一般都支持 `blob:` URL 中的 `application/pdf` 内联预览；
- 移动端或少数浏览器可能表现为下载，这属于浏览器能力差异，非系统缺陷。

2. 安全性
- 预览接口仍然严格依赖后端权限与路径安全校验；
- 前端仅在内存中持有 Blob，不会泄露到外部站点；
- `<iframe src="blob:...">` 的安全边界受浏览器控制，不引入额外的跨域风险。

3. 性能
- 对当前测试的 100KB~数 MB 级别 PDF 文件，生成 blob URL 的开销很小；
- 预览性能主要取决于浏览器内置 PDF Viewer 与机器本身性能；
- 对极大 PDF（数百 MB）建议后续在前端增加提示或限制预览，以避免占用过多内存。

4. 与未来扩展方案的关系
- doc/ppt → PDF 转换预览方案仍然保留在“暂时搁置修复事项”中；
- 未来若希望引入更强大的前端 PDF 交互（分页、缩略图、批注等），可以基于 pdf.js 重新设计一套“完全本地化的 pdf.js 渲染方案”，包括：
  - 本地打包 pdf.worker；
  - 不依赖外网 CDN；
  - 在前端设置可控的渲染行为。

本次方案的定位是：**在不再修改后端、网络无法访问外网 CDN 的前提下，提供一个稳定、简单的 PDF 预览路径，优先保证功能可用与行为可预期。**
