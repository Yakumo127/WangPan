# 验证码登录校验接入 — 变更说明与操作指南（2025-11-11 10:39）

本文件详细记录“验证码未参与登录校验”的修复全过程：设计目标、接口/代码变更、前端改造、测试用例、安全与回滚策略。用于交付与复盘，帮助后续团队维护与扩展。

---

## 1. 背景与目标
- 背景：原系统虽提供获取验证码接口，但登录逻辑未实际校验验证码，无法对撞库与暴力尝试提供有效防护。
- 目标：
  - 在登录流程中引入“带 key 的一次性验证码”校验；
  - 达到“连续失败 ≥3 次必须验证码”的安全阈值；
  - 兼顾用户体验：非强制场景下验证码为可选，提交了就校验；
  - 兼容原接口，不破坏既有前端逻辑。

## 3. API 变更与契约

### 3.1 新增：获取带 key 的验证码
- 方法/路径：`GET /api/auth/captcha/new`
- 鉴权：匿名放行
- 响应（JSON）：
```
{
  "key": "b6d7e2c0-62b7-4b4e-8a4e-0b19a9c7e5cd",   // 一次性验证码标识
  "imageBase64": "data:image/png;base64,iVBORw0KGgo...",
  "expiresIn": 300                                 // 过期秒数
}
```
- 说明：
  - 该 key 对应服务端保存的“答案（小写）”；
  - 校验后立即移除（一次性）；
  - 5 分钟 TTL 自动失效；
  - 保留原有 `GET /api/auth/captcha`（仅返回图片），但推荐新接口（JSON）用于 SPA 场景。

### 3.2 登录（请求体扩展）
- 方法/路径：`POST /api/auth/login`
- 请求体（扩展字段向后兼容）：
```
{
  "username": "string",
  "password": "string",
  "captchaKey": "string, 可选",
  "captcha": "string, 可选"
}
```
- 验证逻辑：
  - 若该用户 loginAttempts ≥ 3，则必须携带正确的 `captchaKey+captcha`；
  - 若 < 3：如果前端带了 captchaKey+captcha，则进行校验，错误则直接失败；
  - 认证顺序：验证码（必要时）→ 用户名/密码 → 成功清零 attempts，失败 attempts++，≥5 锁定。
- 错误提示：
  - “请先输入验证码”（必须验证码但缺失时）
  - “验证码错误或已过期”（验证码错误/过期）
  - “用户名或密码错误”（认证失败，计数累加）
  - “账户已被锁定，请联系管理员”（≥5 次失败）

### 3.3 管理员登录（同策略）
- 方法/路径：`POST /api/auth/admin-login`
- 策略：与普通登录相同（≥3 次失败强制验证码；≥5 锁定），先校验是否 ADMIN 角色。

## 4. 后端实现细节
- CaptchaService（key→answer 存储，TTL 5 分钟，一次性）：
  - 文件：`backend/src/main/java/com/filemanager/service/CaptchaService.java`
  - 新增 `generateCaptchaPair()`：返回 `(key, text)`；
  - 修改 `validateCaptcha(String key, String input)`：大小写不敏感，校验成功后移除；
  - 保留 `generateCaptcha()`（兼容旧图片接口）。
- AuthController：
  - 文件：`backend/src/main/java/com/filemanager/controller/AuthController.java`
  - 新增 `GET /api/auth/captcha/new` 返回 `{ key, imageBase64, expiresIn }`；
  - 原 `GET /api/auth/captcha` 保留（兼容）；
  - userinfo 与其他接口未受影响。
- UserLoginDTO：
  - 文件：`backend/src/main/java/com/filemanager/dto/UserLoginDTO.java`
  - 新增字段：`captchaKey`（String）。
- UserService（登录与管理员登录）：
  - 文件：`backend/src/main/java/com/filemanager/service/UserService.java`
  - 在认证前引入验证码校验逻辑；
  - 失败计数与锁定策略沿用原有（≥5 锁定）。
- SecurityConfig：
  - 既有配置已放行 `/api/auth/**`，无需额外变更；`/api/auth/captcha/new` 自动匹配放行。

## 6. 使用示例（前后端联调）
1) 获取验证码：
```
GET /api/auth/captcha/new
响应: { key, imageBase64, expiresIn }
```
2) 登录提交：
```
POST /api/auth/login
{
  "username": "demo",
  "password": "demo123",
  "captchaKey": "<上一步返回的key>",
  "captcha": "aBZ9qK"
}
```
3) 行为：
- 若用户错误次数≥3，未带验证码则返回“请先输入验证码”；
- 带错验证码返回“验证码错误或已过期”；
- 验证码正确+密码正确 → 登录成功，attempts 清零。

## 7. 测试用例（建议全量验证）
- 正常登录成功（未显示验证码）。
- 输入错误密码 3 次后第 4 次：必须验证码；验证码正确后密码正确→成功。
- 验证码复用：同一 key 二次提交，第二次失败。
- 验证码过期：5 分钟后使用同 key 提交失败。
- 管理员登录：与普通用户一致的验证码策略。
- 锁定策略：连续失败≥5 次后提示锁定，正确验证码也不可登录。
- 兼容性：老页面/脚本若仍访问 `/api/auth/captcha`，行为不受影响。

---

## 8. 安全与边界说明
- 一次性验证码 + TTL 有效期，抵御复用；
- 大小写不敏感，降低输入错误率；
- 阈值触发策略（≥3）兼顾体验与安全；
- 管理员也走同策略，避免成为弱口令入口；
- 若需更强：可加入滑块/行为校验、IP 频率限制、跨端绑定（key 与 UA/IP 绑定）等。

---

## 9. 回滚与开关建议
- 快速回滚：在 UserService 中临时跳过验证码校验（或将阈值设为极大值）；
- 配置化（可后续增强）：在 `application.yml` 增加 `security.captcha.enabled`、`security.captcha.threshold`；
- 不建议移除新接口，以免影响前端新逻辑。
