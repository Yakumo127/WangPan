# 大文件哈希 Web Worker 增强（搁置事项记录，2025-11-20 20:12）

## 一、背景与现状

当前前端已实现：

- 在 `frontend/src/utils/fileHash.js` 中通过增量 SHA-256 实现流式哈希计算，按分块方式对文件进行 SHA-256 计算，支持 4GB 级别单文件；
- 在 `useUploadQueue` 中使用 `computeFileSha256(file, { chunkSize, onProgress, signal })`，结合 AbortController 实现 hash 阶段的暂停/取消；
- 整个哈希计算仍在主线程执行，通过 async/await 与分块读取尽量降低 UI 阻塞，但在超大文件且 CPU 吃紧时，主线程仍可能出现轻微卡顿。

在未来面向生产环境的大规模场景，尤其是在浏览器前端可能执行多任务（上传 + 浏览/预览/其他操作）的情况下，将大文件哈希计算迁移到 Web Worker 中，可以进一步提升应用的平滑度与响应性。

## 二、问题动机

1. 主线程压力：
   - 即便采用分块 + async/await，哈希计算仍在主线程执行，会占用一定时间的 JS 执行片段；
   - 在用户同时进行其他操作（滚动、点击、预览 PDF 等）时，可能感知到 “轻微顿挫”。

2. 多任务场景下体验优化：
   - 当用户同时上传多个大文件、且在系统中浏览其他页面时，理想状态是：  
     - 上传和哈希尽可能在后台“悄悄跑”；  
     - 主 UI 的交互（切 tab、点击按钮、预览等）几乎不受影响。

3. 资源隔离与更好监控：
   - 将大文件哈希搬到 Web Worker，有助于逻辑上隔离 CPU 密集任务，未来也便于在 Worker 侧对哈希统计、限速等进行独立管理。

基于上述原因，计划在适当时机再推进 “大文件哈希 Web Worker 化” 的增强，目前作为搁置事项记录在案。

## 三、拟议方案概要

> 详细方案参考《文件管理新版_上传暂停大文件与续传增强设计_20251120-1916.md》第三部分“极大文件（4GB）哈希计算设计”中的 Web Worker 扩展建议，本处仅做要点摘录。

1. 新增 `hashWorker.js` / `hashWorker.ts`：
   - Worker 接收消息结构：
     - `{ type: 'start', file, chunkSize }`：开始对指定文件进行流式哈希；
     - `{ type: 'abort' }`：中途取消哈希计算。
   - Worker 内部逻辑：
     - 使用现有的增量 SHA-256 实现，对 `file` 做分块读取并 `update`；
     - 每处理完一个块，通过 `postMessage({ type: 'progress', loaded, total })` 报告进度；
     - 完成后发送 `{ type: 'done', hash }`；
     - 捕获异常后发送 `{ type: 'error', message }` 并结束。

2. 主线程 `computeFileSha256` 调整为 Worker 封装：
   - 在 `fileHash.js` 中新增 Worker 封装版本：
     - 创建 Worker 实例；
     - 发送 `start` 消息，并监听 `message` 事件：
       - `progress` 时调用上传队列传入的 `onProgress` 回调；
       - `done` 时 resolve 最终 hash；
       - `error` 时 reject；
     - 结合 AbortController：
       - `signal.aborted` 时向 Worker 发送 `abort` 消息，并 `worker.terminate()`；
       - 抛出带 `code = 'HASH_ABORTED'` 的错误给上传队列。

3. 与现有 useUploadQueue 的集成：
   - 对 `useUploadQueue` 的调用方保持接口不变（仍为 `computeFileSha256(file, { signal, onProgress })`），内部具体实现从“主线程流式哈希”切换为“Worker 流式哈希”；
   - 暂停/取消逻辑不需要修改，只需新增 “通知 Worker 终止工作” 的逻辑。

## 四、实施优先级与风险

优先级：

- 当前流式哈希实现已经可以满足大部分场景的功能需求，Worker 化属于体验优化与资源隔离上的进一步提升；
- 建议在系统进入真实负载环境、观察到明显的主线程卡顿或 CPU 峰值问题时，再作为专项优化项排期实现。

风险与考虑：

1. 浏览器兼容性：
   - 现代浏览器对 Worker 与 File 支持较好，但需要在设计时评估最低浏览器版本要求；
   - 在不支持 Worker 的环境可以 fallback 至主线程流式哈希。

2. 调试与监控复杂度：
   - 将逻辑拆到 Worker 后，调试路径增加，需要配合 source map 与日志方案做好问题定位。

3. 包体积与构建复杂度：
   - 引入 Worker 构建配置（如 vue-cli 的 worker-loader 或 Vite 的 worker 支持），需谨慎评估构建链路的变化。
