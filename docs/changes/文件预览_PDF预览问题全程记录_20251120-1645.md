# 文件预览：PDF 预览问题全程记录（2025-11-20 16:45）

> 本文聚焦于“PDF 文件预览”这一条线，从最初需求、问题暴露、几轮方案尝试到当前阶段性结果，做一次完整复盘，便于后续维护与扩展。

## 一、起点：从“下载”为主到“预览”需求提出

1. 初始状态
- 系统原先以“下载”为主：
  - 前端通过 Axios 请求 `/api/files/download/{id}`，`responseType: 'blob'`，手动创建 a 链接触发下载；
  - 大文件（约 6MB）时，Axios 出现 `timeout of 10000ms exceeded`，暴露出前端超时与下载实现的局限。

2. 下载体验与性能优化
- 针对大文件下载超时问题，设计并实现了“下载直链 + 一次性 token”方案：
  - 后端新增 `/api/files/{id}/download-url` 与 `/api/files/direct-download?token=...`；
  - 前端改为获取直链 URL 后，让浏览器原生下载；
  - 提升了下载可靠性和用户体验。

3. 从“下载”到“预览”的需求
- 在下载问题缓解后，提出新的需求：
  - 单击文件名即为“预览”，而不是直接下载；
  - 图片在当前列表页以大号 `el-dialog` 弹出预览；
  - 其他文件（PDF、Office 等）进入单独预览路由页；
  - 预览能力（可预览的后缀）可在“系统设置”中配置；
  - 预览与下载的权限逻辑相似，但在实现上要**独立**；同时要记录预览成功与失败的审计日志。

## 二、第一轮实现：预览接口 + 基本前端交互

1. 后端：预览接口与预览配置
- 新增系统配置：
  - `SystemSettingService.KEY_PREVIEW_ALLOWED_SUFFIXES`；
  - 可配置默认可预览后缀：`doc, docx, ppt, pptx, pdf, txt, mp4, jpg, jpeg, png`。
- 新增接口：
  - `GET /api/files/{fileId}/preview`：
    - 校验登录态（普通用户 / 管理员）；
    - 校验文件所有权 / 访问权限；
    - 校验扩展名是否在可预览白名单中；
    - 使用 `StreamingResponseBody` 直接输出文件流；
    - `Content-Disposition: inline; filename="..."`；
    - 预览成功/失败调用 `AuditLogService` 记录审计日志。
  - `GET /api/files/preview/config`：返回可预览后缀列表，供前端判断。

2. 前端：文件列表与预览路由
- 列表页 `List.vue`：
  - 根据 `/files/preview/config` 返回的后缀列表，标记哪些文件名可点击预览；
  - 图片（`jpg/jpeg/png`）点击 → 通过 `/preview` 获取 Blob → `el-dialog` 中 `<img :src="blobUrl">` 预览；
  - 其他类型 → 跳转到 `FilePreview` 路由。
- 预览页 `Preview.vue`：
  - 初版实现为：
    - Axios `previewFileApi(id)`，`responseType: 'blob'`；
    - 文本类型：`blob.text()` → `<pre>`；
    - 其他类型（包含 PDF）：`URL.createObjectURL(blob)` → `<iframe :src="blobUrl">`。

3. 第一轮暴露的问题
- PNG 图片预览无反应：对话框 UI 未接入 / 未设置 `imagePreviewVisible`；
- PDF 预览：
  - 请求 `/preview` 时 Axios 报 `ECONNABORTED`（超时），页面提示“网络错误，请检查您的网络连接”；
  - 在某些时刻 `/preview` 返回 403（地址栏直接访问）或 200 但无法在 iframe 中正常展示；
  - 暴露出预览接口 streaming 实现与前端 Axios 使用之间的兼容性问题。

## 三、第二轮：图片修复 + 尝试 iframe 直连 PDF

1. 图片预览修复
- 为列表页补充图片预览对话框：
  - `previewImage(file)` 中请求 `/files/{id}/preview`，生成 blob URL；
  - 使用 `v-model="imagePreviewVisible"` 控制 `el-dialog`；
  - 避免用户点击图片文件名却没有任何界面反馈的问题。

2. PDF 预览尝试：iframe 直连
- 将 PDF 预览改为 `iframe` 直接加载 `/api/files/{id}/preview`：
  - 期望交给浏览器内置 PDF Viewer 处理，绕开 Axios 超时；
  - 但在浏览器中出现：
    - `X-Frame-Options: deny` 导致无法在 iframe 中展示（某些路径）；
    - 地址栏直接访问 `/preview` 返回 403（未携带 Authorization 时）；
    - 在应用内（携带 JWT）访问时，状态码 200 但仍存在行为异常。

3. 此阶段的结论
- 直接依赖“后端 streaming + iframe 直连”在当前部署环境下行为不稳定：
  - 有时会超时、有时 403、有时 200 但无法正常展示；
  - 问题既与后端实现（StreamingResponseBody）相关，也与代理配置和安全头相关。

## 四、第三轮：接入 pdf.js，尝试前端完全控制 PDF 渲染

1. 方案思路
- 为了更可控地渲染 PDF，提出使用 pdf.js 的方案：
  - 由前端接入 `pdfjs-dist`；
  - 通过 Axios 获取 PDF Blob，再由 pdf.js 在 `<canvas>` 中渲染；
  - 预期优点：
    - 不再依赖浏览器内置 PDF Viewer；
    - 可以跨浏览器提供一致的渲染效果和可控的交互能力；
    - 和后端 `/preview` 的 streaming 行为解耦（只要 Axios 能拿到 Blob）。

2. 实际实现
- 前端：
  - 新增 `PdfViewer.vue` 组件，接入 `pdfjs-dist/build/pdf`；
  - 在 `Preview.vue` 中：
    - 为 PDF 类型添加 `viewerType === 'pdf'` 分支：
      - `blob.arrayBuffer()` → `Uint8Array` → `<PdfViewer :data="pdfData" />`；
    - 文本、视频、其他类型保持原有逻辑。
  - 在类型判定上，先只依赖路由上的文件名扩展名，后续又补上了响应头 `Content-Type` + 扩展名的综合判断。

3. 新暴露的问题
- 在用户环境中，pdf.js 报错：
  ```text
  PDF 渲染失败: Error: Setting up fake worker failed:
  "Cannot load script at: https://unpkg.com/pdfjs-dist@3.11.174/build/pdf.worker.min.js"
  ```
- 原因：
  - `PdfViewer.vue` 配置了 `GlobalWorkerOptions.workerSrc` 指向外网 CDN；
  - 当前运行环境无法访问 `unpkg.com`；
  - pdf.js 无法加载 worker 脚本，fake worker 也 setup 失败，导致整个渲染过程抛异常；
  - 进一步引发 Vue 渲染错误（`Cannot read properties of null (reading 'insertBefore')` 等）。

4. 阶段性结论
- pdf.js 方案虽然从架构上更灵活，但在**网络受限环境**下引入了新的外部依赖问题：
  - Worker 无法从外网加载；
  - 即便后端 `/preview` 请求已经按时完成，前端渲染仍然失败；
  - 对当前环境而言，“pdf.js 方案”不具备可用性。

## 五、第四轮：定位“请求长期未完成”的根因（StreamingResponseBody）

1. 关键观察
- Network 显示：
  - `/api/files/{id}/preview` 状态码 200；
  - 大小约 158KB；
  - 有完整的“等待/下载”耗时统计；
  - 但提示“注意：请求尚未完成！”；
- 前端现象：
  - `await previewFileApi(id)` 长时间不返回；
  - `loading` 无法在 `finally` 中关闭；
  - 不论 iframe 还是 pdf.js，都无法顺利执行后续渲染逻辑。

2. 后端 Streaming 实现的局限
- 预览接口使用 `StreamingResponseBody`，且未设置 `Content-Length`：
  - 依赖容器与代理在 streaming 完成后正确关闭连接；
  - 在当前由 18800 与本地代理 10808 组成的链路中，这一行为并非总是“可见地”结束；
  - 浏览器认为连接仍然开放，Network 显示“尚未完成”。

3. 解决方案：改用 Resource + Content-Length
- 将 `previewFile(...)` 的返回类型从 `ResponseEntity<StreamingResponseBody>` 改为 `ResponseEntity<Resource>`：
  - 使用 `FileSystemResource` 封装物理文件；
  - 使用 `Files.size(filePath)` 设置 `Content-Length`；
  - 增加路径归属存储根目录的安全校验；
  - 保留/补充审计日志记录；
  - 使浏览器与 Axios 在读取完指定长度后可以可靠地认为请求“已经完成”。

4. 修复后的效果
- `/preview` 请求在 Network 中不再显示“尚未完成”，而是在合理时间内完成；
- `await previewFileApi(id)` 可以成功 resolve；
- 预览页能够拿到完整 Blob，为后续渲染打下基础。

## 六、第五轮：类型识别修正（Content-Type + 扩展名）

1. 原问题
- 初始的 `viewerType` 判定仅依赖路由上的 `?name=` 扩展名：
  - 若文件在系统中被重命名为不带 `.pdf` 的显示名（如“发票”），则 `viewerType` 不能被判定为 `pdf`；
  - 即使后端返回 `Content-Type: application/pdf`，前端仍将其视为“未知类型”或 office；
  - 导致 pdf.js 或 iframe 的分支无法进入预期的 PDF 渲染路径。

2. 修正方案
- 在 `Preview.vue` 中引入响应头 + 扩展名的综合判定：
  - 优先使用 `res.headers['content-type']` 判定 PDF、文本、视频；
  - 扩展名作为辅助信息（处理 mp4 与 txt/log/md 等）；
  - 将 `viewerType` 由计算属性改为响应式状态，在请求完成后动态设置。

3. 效果
- 只要后端返回 `Content-Type: application/pdf`，无论路由上的名称是否含 `.pdf` 后缀，`viewerType` 都能正确识别为 `'pdf'`；
- 为后续“统一用 iframe 渲染 PDF”打好基础。

## 七、最终阶段方案：回到“浏览器原生 PDF 预览”

1. 问题回顾
- 在后端修复 `/preview` 请求长期未完成、前端修正类型识别后，pdf.js 的主要拦路虎变成：
  - worker 脚本依赖外网 CDN；
  - 当前网络无法访问导致 `fake worker failed`；
  - 直接阻断 pdf.js 渲染链路。

2. 最终选定方案
- 按用户要求，选择“不再改后端，用浏览器原生渲染 PDF”的方案：
  - 继续使用 Axios 调用 `/files/{id}/preview` 获取 Blob；
  - 对于 PDF 类型：
    - 如果 Blob 类型不是 `application/pdf`，强制构造 `new Blob([blob], { type: 'application/pdf' })`；
    - 使用 `URL.createObjectURL(finalBlob)` 生成 `blob:` URL；
    - 在预览页用 `<iframe :src="blobUrl" />` 展示，将 PDF 渲染交给浏览器内置 Viewer；
  - 文本仍用 `<pre>`，视频用 `<video>`，Office 与其他类型也统一走 `<iframe>` 分支。

3. 前端调整要点
- `Preview.vue`：
  - 删除 pdf.js 相关引用和状态（`PdfViewer`、`pdfData` 等）；
  - 保留 `viewerType` 判定逻辑，但将 PDF、Office、其它二进制统一走 blob + iframe；
  - 模板仅保留三种分支：
    - 视频 → `<video :src="blobUrl" />`；
    - 文本 → `<pre>{{ textContent }}</pre>`；
    - 其余 → `<iframe :src="blobUrl" />`。
- `PdfViewer.vue` 和 `pdfjs-dist` 依赖暂时保留在项目中，但不再被引用，不会影响运行。

4. 当前状态
- 图片预览：通过列表页弹出对话框预览，已正常；
- 文本预览：通过 `blob.text()` + `<pre>` 展示，已正常；
- 视频预览：通过 `<video>` 播放，已正常；
- PDF 预览：通过 `<iframe src="blob:...">` 交给浏览器内置 PDF Viewer 渲染，在当前环境下已能够稳定预览。

## 八、经验总结与后续建议

1. 对预览接口的经验
- StreamingResponseBody 在理论上适合大文件和实时流，但在存在多层代理的环境下：
  - 若不设置 `Content-Length`，连接结束语义容易被中间层处理得不够“可见”，导致浏览器认为请求长期未完成；
  - 对前端使用 `await` 模式的代码极不友好。
- 更稳妥的做法是：
  - 对普通预览场景使用 `Resource + contentLength`；
  - 将 streaming 用于明确需要流式推送的场景，并逐一验证链路行为。

2. 对前端预览实现的经验
- 预览实现层次上可以分两类：
  - “浏览器原生能力型”（PDF、图片、视频等），尽量交给浏览器内置能力处理，前端只负责提供正确的 MIME 类型和 URL；
  - “前端自渲染型”（pdf.js、Office 转 PDF 等），要对依赖的脚本来源、网络环境有充分掌控（例如本地打包 worker）。
- 当前环境网络受限，优先使用“浏览器原生能力”是一条稳妥路径。

3. 类型识别策略
- 仅依赖文件名扩展名容易出错，尤其是系统允许用户重命名文件显示名时；
- 综合使用响应头 `Content-Type` + 扩展名可以显著提高判断准确性；
- 建议在设计阶段就明确“类型判定”的优先级和策略，以减少前后端理解偏差。

4. 文档与变更规范的重要性
- 每一次关键调整（预览接口实现、pdf.js 接入与回退、类型识别修正）都对应独立的设计/变更文档，并在 `文档变更总记录` 中登记；
- 便于追踪“为什么这么做”“什么时候做的”“有哪些权衡”，对后续维护与新成员理解系统行为都非常有价值。

整体而言，PDF 预览从“下载为主”演进到“预览为主”的过程中，经历了多轮尝试和回退。当前阶段选择在现有环境下更稳妥的“浏览器原生 PDF 预览”方案，后续如网络环境或需求变化（例如需要高度定制的 PDF 交互），仍可在已有经验基础上重新评估 pdf.js 或其他方案的引入时机与方式。
