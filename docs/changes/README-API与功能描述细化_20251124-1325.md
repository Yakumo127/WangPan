# README API 与功能描述细化（2025-11-24 13:25）

## 问题成因
- 在上一轮对根目录 `README.md` 的重写中，已经按 2.x 实现对整体结构进行了对齐，但 API 章节与“已实现功能”部分仍偏向概要说明，缺少字段级、参数级的约束说明以及与代码实现的一一对应介绍。
- 随着项目引入了分片上传、秒传、版本管理、下载直链、管理员分页检索等一系列能力，仅靠现有几条示例接口难以支撑前后端协作与三方对接，对不了解代码的新同学不够友好。
- “已实现功能”列表对各能力仅做了单行概述，例如“文件上传（支持大文件）”“文件分片上传与断点续传”等表述没有展开具体行为、边界条件与配套接口，难以形成一份可直接用于需求确认与回归测试的功能清单。

## 排查过程与历史
- 阅读当前 `README.md` 中“🔌 API 接口文档”章节，确认已经覆盖：
  - 认证相关接口：注册、登录、管理员登录、用户信息、验证码、资料更新、修改密码等；
  - 文件管理接口：普通上传、列表查询、下载、删除、重命名、一次性下载直链；
  - 文件夹管理接口：创建、列表；
  - 管理员接口：用户列表、管理员恢复文件；
  - 回收站接口：个人回收站列表、管理员清空所有回收站。
- 对照后端控制器代码：
  - `backend/src/main/java/com/filemanager/controller/FileController.java`
    - 发现分片上传相关接口：`POST /api/files/chunk`、`POST /api/files/merge`、`GET /api/files/chunk/status`，以及秒传相关接口：`POST /api/files/exists`、`POST /api/files/exists-global`；
    - 发现版本管理相关接口：`GET /api/files/{fileId}/versions`、`POST /api/files/{fileId}/versions/revert`、按版本号下载 `GET /api/files/download/{fileId}/version/{versionNo}` 等；
    - 发现文件移动/复制接口：`POST /api/files/{fileId}/move`、`POST /api/files/{fileId}/copy`，搜索接口 `GET /api/files/search`，以及管理员分页查询接口 `/api/files/admin/list`、管理员下载 `/api/files/admin/download/{fileId}`；
    - 发现回收站接口不仅包括 `GET /api/files/recycle/bin`，还包含管理员回收站列表 `/api/files/admin/recycle/bin` 等更丰富的能力。
  - `backend/src/main/java/com/filemanager/controller/FolderController.java`
    - 除了 `POST /api/folders/create` 与 `GET /api/folders/list` 外，还包括：`DELETE /api/folders/{folderId}`、`PUT /api/folders/{folderId}/rename`、`POST /api/folders/{folderId}/move`、`POST /api/folders/{folderId}/copy`、`GET /api/folders/{folderId}/path` 等接口。
- 对照“✨ 已实现功能”部分，确认功能描述已经覆盖主要能力，但存在以下不足：
  - 分片上传与秒传仅在“性能优化”和“文件管理”中简要提到，未明确分片流程（探测 → 分片上传 → 合并）与失败恢复策略（分片状态查询、缺失分片列表）；
  - 版本管理仅提到“版本列表、指定版本下载与回滚”，未说明版本号增长策略、回滚实现方式（追加一个指向旧 Blob 的新版本）以及与配额的关系；
  - 回收站与管理员排期删除已在实体字段中体现（`owner_hidden`、`admin_delete_*`），但功能描述部分没有将“冷静期”“排期删除”“彻底不可恢复”等概念讲清楚；
  - 管理员列表查询、审计日志筛选等能力在 README 中只被一句话带过，不利于运维同学快速理解系统的管理能力边界。

## 修复建议
- 在保持 README 现有标题层级与章节结构不变的前提下，对 API 章节进行“横向补全 + 纵向细化”：
  - 横向补全：将分片上传/合并/状态查询、秒传检查、版本管理（版本列表、按版本下载、版本回滚）、文件移动/复制、搜索、管理员分页列表与管理员回收站等接口以小节或说明的形式补入文档，确保和主要业务路径相关的接口在 README 中都有“入口”；
  - 纵向细化：对现有接口增加更多细节说明，例如：是否需要鉴权、角色要求、请求/响应字段含义与范围、常见错误码/错误消息、分页参数默认值与边界、典型使用流程示例（如分片上传完整流程）。
- 对“✨ 已实现功能”及其下属小节（用户功能、文件管理、文件夹管理、回收站功能、管理员功能、系统特性、前端界面等）进行“功能视角”的展开说明：
  - 在不删减现有条目的前提下，为关键功能增加括号内或附行说明，描述实际行为、依赖的 API、大致的流程与异常场景处理方式；
  - 对“性能优化”中的分片上传、秒传、缩略图生成等条目补充背后的机制，如 `file_chunks` 表、Blob 去重、下载多 Range 支持等。
- 将本次“API 与功能描述细化”视为一次新的文档变更：
  - 在 `docs/changes` 目录中新增一份专门报告，记录动机、分析过程、调整建议与已实施内容（即本文件）；
  - 在 `docs/文档变更总记录.md` 中追加记录行，指向该报告与 `README.md`，便于追踪 README 的多次演进。
