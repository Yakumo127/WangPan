# 文件预览：PDF 类型识别与 pdf.js 渲染路径修正（2025-11-20 16:15）

## 一、问题背景与症状

- 用户在部署最新代码后，点击 PDF 文件名进入预览页：
  - Network 中 `/api/files/{id}/preview` 请求状态为 `200 OK`，响应耗时约 260ms，`Content-Type: application/pdf`，内容大小约 158KB；
  - 控制台无明显 `加载预览失败` 或 `PDF 渲染失败` 日志；
  - 页面上仍表现为“长时间转圈”，且在 DOM 结构中查找不到 `<div class="pdf-viewer">` 节点；
  - 同时在返回文件列表时，`/api/files/list`、`/api/folder/list`、`/api/files/preview/config` 等接口出现 `timeout of 10000ms exceeded` 的 Axios 超时，这属于后端/网络在某一时刻变慢，与 PDF 组件渲染逻辑相对独立。

由上述现象可以推断：

1. 预览接口本身工作正常：HTTP 层 200 + 正确的 `Content-Type: application/pdf` + 文件本地可打开；
2. 预览页 `Preview.vue` 中的 pdf.js 组件 `PdfViewer` 并未真正渲染出来（DOM 中没有 `.pdf-viewer` 节点），说明：
   - 要么前端没有走到 `viewerType === 'pdf'` 这一分支；
   - 要么 `pdfData` 始终为 `null`，导致 `<PdfViewer v-if="pdfData">` 未挂载；
3. 由于外层仍在等待渲染结果，用户体验上表现为“一直转圈”，容易误以为是预览接口问题。

## 二、问题成因分析

### 1. 原有 PDF 类型判定逻辑存在局限

在接入 pdf.js 之前，`Preview.vue` 中的预览类型判定使用的是一个基于文件名扩展名的计算属性：

```js
const filename = computed(() => (route.query.name || '').toString())

const getExt = () => {
  const name = filename.value || ''
  const idx = name.lastIndexOf('.')
  if (idx < 0) return ''
  return name.slice(idx + 1).toLowerCase()
}

const viewerType = computed(() => {
  const ext = getExt()
  if (['pdf'].includes(ext)) return 'pdf'
  if (['mp4'].includes(ext)) return 'video'
  if (['txt', 'log', 'md'].includes(ext)) return 'text'
  if (['doc', 'docx', 'ppt', 'pptx'].includes(ext)) return 'office'
  return 'unknown'
})
```

即：

- 仅依赖路由上的 `?name=xxx` 参数（通常由 `List.vue` 中的 `row.originalFilename || row.name` 传入）来判断文件类型；
- 如果该名称没有 `.pdf` 后缀（例如用户在系统中将显示名改为“发票”而未包含扩展名），则 `viewerType` 会被判定为 `unknown`；
- 在这种情况下，即便后端返回的实际上是 `Content-Type: application/pdf` 的 PDF 文件，前端也会走“未知类型/office 类型”的分支，而不会进入 pdf.js 渲染路径。

这会导致两类问题：

1. PDF 文件被错误地当作“未知二进制”，继续走 `<iframe :src="blobUrl">` 的旧路径，回到之前“浏览器内置 PDF Viewer 对 blob 源兼容性不好”的老问题；
2. 由于 pdf.js 分支依赖 `viewerType === 'pdf'` 且 `pdfData` 非空，任何一个条件不满足，`PdfViewer` 组件都不会挂载，DOM 中看不到 `.pdf-viewer` 节点。

### 2. 接入 pdf.js 后未结合响应头信息

在第一次接入 pdf.js 时，仅在前端通过扩展名判定 `viewerType`，并在 `viewerType === 'pdf'` 时将 `blob.arrayBuffer()` 转换为 `Uint8Array`，传给 `PdfViewer`：

```js
if (viewerType.value === 'text') {
  textContent.value = await blob.text()
} else if (viewerType.value === 'pdf') {
  const buffer = await blob.arrayBuffer()
  pdfData.value = new Uint8Array(buffer)
} else {
  const url = window.URL.createObjectURL(blob)
  blobUrl.value = url
}
```

由于没有使用后端返回的 `Content-Type` 信息，当路由上的文件名缺失 `.pdf` 时，`viewerType` 无法被判定为 `'pdf'`，整个 pdf.js 渲染路径完全被绕过。

## 三、本次修复方案

核心思想：**不再仅依赖路由文件名扩展名，而是综合“响应头的 Content-Type + 扩展名”动态判定预览类型**，确保只要接口返回的是 `application/pdf`，就一定走 pdf.js 渲染路径。

### 1. 将预览类型由计算属性改为响应式状态

原先的：

```js
const viewerType = computed(() => { ... })
```

改为：

```js
const viewerType = ref('unknown')
```

并在 `loadPreview` 请求成功后，根据 `headers + 扩展名` 来更新 `viewerType`：

```js
const res = await previewFileApi(fileId.value)
const blob = res?.data
if (!(blob instanceof Blob)) {
  throw new Error('预览数据无效')
}

const ext = getExt()
const contentType = (res && res.headers && (res.headers['content-type'] || res.headers['Content-Type'])) || ''

let type = 'unknown'
if (contentType && contentType.includes('application/pdf')) {
  type = 'pdf'
} else if (contentType.startsWith('video/') || ext === 'mp4') {
  type = 'video'
} else if (contentType.startsWith('text/') || ['txt', 'log', 'md'].includes(ext)) {
  type = 'text'
} else if (['doc', 'docx', 'ppt', 'pptx'].includes(ext)) {
  type = 'office'
}
viewerType.value = type
```

这样即使 `?name=` 中没有 `.pdf`，只要后端返回的是 `Content-Type: application/pdf`，`viewerType` 就会被正确设置为 `'pdf'`。

### 2. 按更新后的 `viewerType` 分流渲染路径

在 `viewerType` 更新后，继续使用统一的分支逻辑：

```js
if (viewerType.value === 'text') {
  textContent.value = await blob.text()
} else if (viewerType.value === 'pdf') {
  const buffer = await blob.arrayBuffer()
  pdfData.value = new Uint8Array(buffer)
} else {
  const url = window.URL.createObjectURL(blob)
  blobUrl.value = url
}
```

模板保持不变：

```vue
<template v-if="viewerType === 'video'">
  <video v-if="blobUrl" class="preview-video" controls :src="blobUrl"></video>
</template>
<template v-else-if="viewerType === 'text'">
  <pre class="preview-text">{{ textContent }}</pre>
</template>
<template v-else-if="viewerType === 'pdf'">
  <PdfViewer v-if="pdfData" :data="pdfData" />
</template>
<template v-else>
  <iframe v-if="blobUrl" :src="blobUrl" class="preview-iframe" />
</template>
```

这样，PDF 类型在任何情况下都会进入 pdf.js 的 `PdfViewer` 渲染分支，而不会再误落到 `<iframe>` 分支。

## 四、影响范围与兼容性评估

1. **对 PDF 预览的影响**
   - 不再完全依赖路由参数中的文件名后缀；
   - 只要后端返回 `Content-Type: application/pdf`，就会强制按 pdf.js 路径进行预览；
   - 解决了“文件显示名不带 .pdf 后缀时无法触发 pdf.js 渲染”的问题。

2. **对文本、视频等类型预览的影响**
   - 文本：优先根据 `Content-Type` 中的 `text/` 前缀判定，其次才看扩展名（`txt/log/md`），行为更稳健；
   - 视频：优先根据 `video/` 前缀判定，其次看 `mp4` 后缀；
   - 文本与视频的模板分支逻辑保持不变，现有预览体验不受影响。

3. **对 Office/其他类型预览的影响**
   - Office 类（`doc/docx/ppt/pptx`）仍然依赖扩展名判定，保留原有 `<iframe :src="blobUrl">` 行为；
   - 未特别识别的类型仍会走 `unknown` 分支，通过 `<iframe>` 尝试内联展示或由浏览器触发下载；
   - doc/ppt → PDF 转换预览方案仍按先前设计归类为“暂时搁置修复事项”，本次不改动。

4. **与后端接口的兼容性**
   - 本次修改完全基于已有的 `/api/files/{id}/preview` 接口返回的 `Content-Type` 头，不需要后端做任何调整；
   - 如后续后端对预览接口增加新的类型（如 `application/vnd.openxmlformats-officedocument.*`），只需在前端根据新类型扩展 `viewerType` 判定即可。

## 五、后续建议

1. **增加调试日志（视需要开启）**
   - 在开发环境中，可以临时增加 `console.log('preview headers', contentType, 'ext', ext, 'blobType', blob.type)` 便于排查；
   - 生产环境建议保持当前简洁日志策略，只在出现异常时打印错误。

2. **在系统设计文档中补充“类型判定策略”**
   - 在 `docs/specs/文件预览功能设计方案_20251120-1324.md` 中补充一节，描述：
     - 前端如何优先依据 `Content-Type` 判定预览类型；
     - 扩展名只作为辅助信息；
     - 以及未来支持新类型的扩展方式。

3. **监控未来可能的性能与兼容性问题**
   - 对极大体积、多页 PDF 文件，可进一步评估 pdf.js 的渲染性能，并考虑分页懒加载等优化；
   - 如生产环境限制外部 CDN，可将 pdf.js worker 迁移到本地静态资源，并在“暂时搁置修复事项”中记录待办。

## 六、小结

- 问题的根本原因在于：前端仅依赖路由参数中的文件名扩展名来识别 PDF，导致某些文件（尤其是显示名不含 `.pdf` 的场景）无法进入 pdf.js 渲染路径，从而继续触发旧的 `<iframe + blob>` 行为，表现为“请求 200 但预览页长期转圈”；
- 本次修复通过引入“基于响应头 Content-Type + 扩展名的动态判定”，保证只要后端返回 `application/pdf`，就必然走 pdf.js 渲染路径，同时保持其他类型的预览行为不变；
- 修改范围集中在 `frontend/src/views/files/Preview.vue`，不影响后端接口与其他前端模块，便于快速验证和回滚。
