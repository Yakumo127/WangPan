# 历史版本未生效（上传同名文件未走版本流程）问题报告

## 问题成因
- 后端已支持通过 `parentId` 创建新版本，但前端上传流程始终未携带 `parentId`，导致每次上传都走“创建新文件”分支。
- 新版文件管理（Explorer + 上传队列）在直传、秒传（quick-create）与分片合并时均固定传 `parentId = null`。
- 旧版文件列表上传同样只提交文件与可选 `folderId`，未识别当前目录的同名文件。

## 排查过程与历史
- 阅读 `FileService.uploadFile` 与控制器，确认只要传入 `parentId` 即会追加 `FileVersion` 并更新激活版本。
- 前端新版上传队列 `useUploadQueue` 的 `checkFastUpload/directUpload/mergeChunks` 均未传递 `parentId`。
- 旧版 `List.vue` 上传逻辑仅构造 `FormData(file, folderId)`，无版本关联参数。
- 确认管理员上传页 `admin/Files.vue` 仅做简单全局上传，不涉及版本管理（本次不改）。

## 修复建议
- 在前端上传前，根据“当前目录 + 文件名”查找已存在的文件，若命中则将其 `id` 作为 `parentId` 传入后端。
- 覆盖直传、秒传（quick-create）和分片合并三条上传链路，保持行为一致。
- 保持变更仅限前端，无需改动后端接口。

## 实际采取的修复操作
- 新增前端同名匹配与 `parentId` 解析逻辑：优先命中当前目录下同名文件，找到即作为版本父文件。
- 新版文件管理（Explorer + useUploadQueue）：秒传 `quick-create`、直传 `upload`、分片合并 `merge` 全部传递解析出的 `parentId`，让同名上传落入历史版本。
- 旧版文件列表上传：在直传与分片合并前同样解析 `parentId`，避免继续生成多条同名记录。
