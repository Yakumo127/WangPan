# 文件预览：pdf.js 组件接入与 PDF 渲染修复（2025-11-20 15:32）

## 一、问题成因回顾

1. 现象描述
- 在系统页面中单击 PDF 文件名进入预览页；
- Network 面板中 `/api/files/{id}/preview` 请求状态为 200，`Content-Type: application/pdf`，大小约 158KB；
- 控制台无报错日志，但预览页一直显示“转圈加载中”，长时间无法看到 PDF 内容；
- 地址栏直接访问 `/api/files/{id}/preview` 时返回 403（这是未携带登录态时的正常权限拦截，与预览页内部请求不同）。

2. 现有实现方式
- 后端通过 `/api/files/{id}/preview` 返回文件流，`Content-Disposition: inline`，`Content-Type` 正确设置为 `application/pdf`；
- 前端 `Preview.vue` 中对所有非文本、非视频类型统一使用：
  - `axios` 以 `responseType: 'blob'` 拉取文件；
  - 调用 `URL.createObjectURL(blob)` 生成 `blob:` URL；
  - 使用 `<iframe :src="blobUrl" />` 将预览交给浏览器内置 PDF/Office 组件处理。

3. 根因分析
- 从返回头和本地下载验证可以确认：
  - 预览接口返回的是合法的 PDF 文件（本地可正常打开）；
  - HTTP 层不存在超时或 403 问题；
  - 问题集中在“浏览器内置 PDF Viewer 对 `blob:` 源的处理”这一层。
- 具体表现为：
  - Axios 请求成功 resolve，`loading` 状态在 `finally` 中被正确关闭；
  - Network 中可以看到完整的 PDF 响应体大小；
  - 但 iframe 内部 PDF Viewer 一直处于自身的 Loading 状态，不向外抛出明显的 JS 错误，导致页面体验是“无报错但始终转圈”。
- 结论：现有“Axios + blob URL + `<iframe>` + 浏览器内置 PDF Viewer”方案在当前浏览器环境下存在兼容性问题，属于渲染层问题，而非接口或权限问题。

## 二、排查过程与历史

1. 排除接口与权限问题
- 对比地址栏直接访问与应用内请求：
  - 地址栏直接访问 `/api/files/{id}/preview` 未携带 `Authorization`，返回 403 + HTML 错误页，这是预期行为；
  - 应用内通过 Axios 请求时，会自动附带 `Authorization: Bearer xxx`，后端正常通过 Spring Security 鉴权后返回 200 + PDF；
  - 二者不矛盾，说明接口安全控制正常。

2. 排除文件本身问题
- 使用已有下载功能将同一份 PDF 下载到本地，使用系统 PDF 阅读器打开，确认文件内容正常无损坏；
- 结合响应头的 `Content-Type: application/pdf` 与 `Content-Disposition: inline`，可以确认后端返回的就是标准 PDF 文件。

3. 聚焦前端渲染路径
- 检查 `Preview.vue` 的实现：
  - 非文本、非视频文件统一走 blob URL + `<iframe>`；
  - PDF 仅通过扩展名识别，未对 blob 内容类型做额外校验；
  - Axios 成功返回后没有进入 `catch` 分支，因此控制台不出现“加载预览失败”日志。
- 结合用户反馈“Network 有 200 + 大小，但页面一直转圈、无错误”，可以推断：
  - Axios 已经收到了完整的二进制数据；
  - 问题发生在 iframe 内部的渲染阶段。

4. 历史修复尝试
- 早期尝试通过调整 Axios 超时时间、改用 iframe 直连 `/preview` 等方式缓解超时与 403 问题；
- 当前问题已经从“超时/403”收敛为“PDF blob 在 iframe 中渲染异常”，说明需要引入更可控的 PDF 渲染方案，而不是继续依赖浏览器内置 PDF Viewer。

## 三、修复方案设计与理由

本次修复采用“基于 pdf.js 的 Vue 组件渲染 PDF”，从根本上绕开浏览器内置 PDF Viewer，核心思路如下：

1. 引入 pdf.js 作为渲染引擎
- 在前端增加依赖：`pdfjs-dist`，使用 Mozilla 官方的 pdf.js 库进行 PDF 解析与渲染；
- 不再依赖浏览器自身的 PDF 插件，对不同浏览器/插件组合提供一致的渲染行为。

2. 新增专用 `PdfViewer` 组件
- 新建 `src/components/PdfViewer.vue`，职责：
  - 接收上游传入的 PDF 二进制数据（`Uint8Array`）；
  - 使用 `pdfjs-dist` 的 `getDocument({ data })` 解析 PDF；
  - 逐页创建 `<canvas>`，通过 `page.render({ canvasContext, viewport })` 将每一页绘制出来；
  - 组件内部管理加载状态与错误状态，并在出现解析/渲染异常时给出明确提示（不再默默转圈）。
- 为简化接入，当前实现采用“逐页垂直排布”的方式展示 PDF，后续可以根据需求扩展缩放、跳页、缩略图等功能。

3. 调整预览页渲染逻辑
- 保持原有“单击文件名进入预览页”的交互不变；
- 在 `src/views/files/Preview.vue` 中按文件类型分流：
  - 文本类（`txt/log/md`）仍使用 `blob.text()` + `<pre>` 展示；
  - 视频类（`mp4`）仍使用 `<video>` 标签 + `blob:` URL 播放；
  - **PDF 文件：改为将 Axios 返回的 `blob` 转成 `ArrayBuffer → Uint8Array` 后传给 `PdfViewer` 组件，由 pdf.js 负责解析与绘制；**
  - 其他类型（如 Office 文档）暂时继续使用 `<iframe :src="blobUrl">` 的方式预览（未来 doc/ppt → pdf 转换预览仍按“暂时搁置修复事项”处理）。

4. Worker 配置与权衡
- 为在不修改构建配置的前提下简化接入，本次实现中通过 pdf.js 提供的 `GlobalWorkerOptions.workerSrc` 指向官方 CDN 版本的 `pdf.worker.min.js`，避免额外配置 webpack worker 打包逻辑；
- 这样可以在保持前端代码仓库简单的情况下，快速验证并稳定 PDF 预览体验；
- 后续如有需要，可以将 worker 文件迁移到本地静态资源目录，并在“暂时搁置修复事项”中补充“PDF worker 本地化部署”的加固项。

5. 方案选择理由
- 兼容性：pdf.js 在各主流浏览器中行为一致，不依赖浏览器 PDF 插件；
- 可控性：渲染过程与错误处理完全掌握在前端代码中，便于记录日志和用户提示；
- 演进空间：未来可以逐步增加分页导航、缩略图、缩放等增强能力，而无需受限于内置 Viewer 的功能。

## 四、实际采取的修复操作（代码级）

> 以下为本次实际实施的核心改动摘要，详细代码请以仓库中的具体文件为准。

1. 前端依赖与组件新增
- 在 `frontend/package.json` 中新增依赖：
  - `"pdfjs-dist": "^3.11.174"`（具体版本以实际写入为准）；
- 新增组件 `frontend/src/components/PdfViewer.vue`：
  - 使用 `pdfjs-dist` 解析 PDF：
    - 在组件初始化时配置 `pdfjsLib.GlobalWorkerOptions.workerSrc` 指向 pdf.js 官方 CDN 的 worker；
    - 在 `onMounted` / `watch` 钩子中监听 `props.data` 变化，触发重新渲染；
  - 渲染逻辑：
    - 清理旧的 canvas 与 pdf 对象（避免内存泄漏）；
    - 调用 `getDocument({ data: props.data })` 获取 `pdfDoc`；
    - 遍历 `pdfDoc.numPages`，依次渲染每一页到单独的 canvas，并追加到容器中；
    - 渲染过程中对异常进行捕获，显示“PDF 预览失败”的用户友好提示。

2. 预览页 `Preview.vue` 改造
- 引入新增组件：
  - `import PdfViewer from '@/components/PdfViewer.vue'`；
- 新增状态：
  - `const pdfData = ref(null)`：用于存放 PDF 的 `Uint8Array` 数据；
- 调整 `loadPreview` 逻辑：
  - 继续通过 `previewFileApi(fileId)` 请求 `responseType: 'blob'` 的预览数据；
  - 若类型为文本（`viewerType === 'text'`）：
    - 调用 `blob.text()`，写入 `textContent`；
  - 若类型为 PDF（扩展名为 `pdf`）：
    - 使用 `await blob.arrayBuffer()` 获取原始二进制；
    - 构造 `pdfData.value = new Uint8Array(buffer)`，交给 `PdfViewer` 渲染；
  - 其他类型保持原有行为，仍使用 `URL.createObjectURL(blob)` 生成 `blobUrl`，通过 `<iframe>` 或 `<video>` 展示；
  - 保留 `try/catch/finally` 结构，确保异常时能给出提示，且不出现“永远转圈”的问题。
- 调整模板：
  - `viewerType === 'video'`：保持 `<video :src="blobUrl" />` 不变；
  - `viewerType === 'text'`：保持 `<pre>{{ textContent }}</pre>` 不变；
  - **新增 `viewerType === 'pdf'` 分支：**
    - 使用 `<PdfViewer v-if="pdfData" :data="pdfData" />` 承载 PDF 渲染；
  - 其他类型仍使用 `<iframe v-if="blobUrl" :src="blobUrl" class="preview-iframe" />`。

3. 其他类型预览的保护
- 本次修改确保：
  - 图片预览仍由文件列表页的对话框逻辑负责，不受 PDF 渲染路径变更影响；
  - 视频、文本预览路径不变，仅 PDF 类型单独走 pdf.js 渲染；
  - 对于暂不支持的 Office 文档，仍可按原有 iframe 行为预览或在未来挂接“doc/ppt → pdf 转换预览”方案。

## 五、安全性与性能评估

1. 安全性
- 预览接口仍然沿用原有的权限校验与审计日志：
  - 只有通过鉴权的已登录用户才能访问 `/api/files/{id}/preview`；
  - 每次预览请求都会记录成功/失败的审计日志（包括文件 ID、文件名、耗时与错误信息）；
  - 不存在绕过权限的新增入口。
- pdf.js 渲染是在浏览器端纯前端完成：
  - PDF 数据未上传到第三方，仅在当前页面内存中解析；
  - 与原有方案相比，安全边界未放宽。
- 唯一新增点是 pdf worker 从 CDN 加载：
  - 当前使用官方/公共 CDN 作为 worker 脚本来源，属于“代码托管在第三方”的权衡；
  - 后续可以在“暂时搁置修复事项”中补充“PDF worker 本地化部署”的待办项，进一步消除对外部 CDN 的依赖。

2. 性能
- 对于当前测试中 158KB 级别的 PDF 文件：
  - pdf.js 渲染性能足够，用户基本无感知延迟；
  - 相比浏览器内置 Viewer，渲染时间处于同一量级。
- 对于大体积、多页 PDF：
  - 目前采用“逐页顺序渲染”的方式，首次加载可能略慢；
  - 未来可以考虑分页懒加载或只渲染当前可视区域的页面，以进一步优化性能。
