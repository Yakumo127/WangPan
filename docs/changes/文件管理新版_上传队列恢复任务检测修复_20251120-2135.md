# 文件管理（新版）上传队列恢复任务检测修复（2025-11-20 21:35）

## 一、问题背景

根据《文件管理（新版）上传功能升级设计_20251120-1858》与后续实现文档（上传队列与直传实现 / 分片与秒传逻辑完善 / 上传暂停大文件哈希与恢复实现），新版文件管理页面 `Explorer.vue` 已接入 `useUploadQueue` 组合函数，以实现：

- 多文件上传队列管理；
- 秒传 + 直传 + 分片上传流程；
- 页面刷新后的任务恢复提示。

在实际打开“文件管理（新版）”页面时，控制台出现如下错误：

```text
ERROR
uploadQueue.some is not a function
TypeError: uploadQueue.some is not a function
    at ComputedRefImpl.eval [as fn] (... Explorer.vue:85:96)
    at refreshComputed (...)
    ...
```

该错误会在 `Explorer.vue` 初始化阶段触发，导致上传队列抽屉逻辑异常，即使页面其他功能勉强可用，也会影响用户体验和后续调试。

## 二、成因分析

### 2.1 设计与实现约定回顾

在设计文档与 `useUploadQueue` 实现中，上传队列的核心约定为：

```js
const uploadQueue = ref([]) // UploadTask[]
const hasRunningTasks = computed(() =>
  uploadQueue.value.some((t) => t.status === 'hashing' || t.status === 'checking_fast' || t.status === 'uploading')
)
```

也就是说：

- `uploadQueue` 是一个 `ref`，其实际数组存放在 `uploadQueue.value` 中；
- 在组合函数内部使用时，需要通过 `uploadQueue.value` 访问数组方法。

`useUploadQueue` 对外暴露的是这个 `ref` 本身：

```js
return {
  uploadQueue,
  hasRunningTasks,
  enqueueFiles,
  pauseTask,
  resumeTask,
  cancelTask,
  retryTask,
  attachFileToTask
}
```

模板中使用 `<el-table :data="uploadQueue">` 时，得益于 Vue 3 的 ref 自动解包机制，可以直接把 `ref` 当作数组来用；但在 `<script setup>` 的普通 JS 逻辑中，**仍然需要显式使用 `.value`**。

### 2.2 Explorer.vue 中的使用错误

问题出自 `frontend/src/views/files/Explorer.vue` 中用于检测“可恢复任务”的计算属性：

```js
const hasRestorableTasks = computed(() =>
  uploadQueue.some(t => !t.file && t.status === 'paused')
)
```

这里存在两个关键点：

1. `uploadQueue` 是从 `useUploadQueue()` 解构出来的 `ref`：

   ```js
   const {
     uploadQueue,
     hasRunningTasks,
     enqueueFiles,
     pauseTask,
     resumeTask,
     cancelTask,
     retryTask,
     attachFileToTask
   } = useUploadQueue({ ... })
   ```

2. 在计算属性中，却直接调用了 `uploadQueue.some(...)`，即把 `ref` 当作原生数组使用。

在 JS 运行时：

- `uploadQueue` 是一个 `RefImpl` 对象，类似 `{ value: [ ...tasks ] }`；
- `RefImpl` 自身没有 `.some` 方法，因此 `uploadQueue.some` 为 `undefined`；
- 在调用 `uploadQueue.some(...)` 时触发：

  ```text
  TypeError: uploadQueue.some is not a function
  ```

这正是错误堆栈中所反映的内容。

### 2.3 模板与脚本行为差异导致的“心理误差”

在同一文件的模板中，`uploadQueue` 的使用方式是：

```vue
<div v-if="uploadQueue.length === 0" ...>暂无上传任务</div>
<el-table v-else :data="uploadQueue" ...>
  ...
</el-table>
```

这些地方并不会报错，是因为：

- 在模板语法中，Vue 会自动对 `ref` 做解包（unref），`uploadQueue` 被当作其 `.value` 使用；
- 所以 `.length` 与作为数组传入 `:data` 都是合法的。

而在 `<script setup>` 中，`uploadQueue` 仍然是一个 `ref`，没有自动解包，因此需要显式 `.value`。这两者行为差异容易导致“在模板里能直接用，在脚本里也可以直接用”的错觉，从而埋下本次错误。

## 三、修复方案与实际改动

### 3.1 修复思路

目标是让 `Explorer.vue` 中“可恢复任务”的检测逻辑与 `useUploadQueue` 的设计保持一致，即：

- 明确 `uploadQueue` 是 `ref<UploadTask[]>`；
- 在脚本中通过 `uploadQueue.value` 访问数组和调用数组方法；
- 保留现有业务判断逻辑：**“没有绑定 file 且状态为 paused 的任务，视为可恢复任务”**。

### 3.2 具体代码改动

文件：`frontend/src/views/files/Explorer.vue`

将原来的：

```js
const hasRestorableTasks = computed(() =>
  uploadQueue.some(t => !t.file && t.status === 'paused')
)
```

修改为：

```js
const hasRestorableTasks = computed(() =>
  uploadQueue.value.some(t => !t.file && t.status === 'paused')
)
```

说明：

- 无任何业务逻辑变化，仅修正对 `uploadQueue` 类型的使用；
- 模板中对 `uploadQueue` 的用法（长度判断与表格数据绑定）保持不变；
- `useUploadQueue` 的实现与设计文档中的 API 约定完全一致，无需修改。

### 3.3 行为验证

1. 打开“文件管理（新版）”页（`Explorer.vue`）：
   - 控制台不再出现 `uploadQueue.some is not a function` 的错误；
   - 页面渲染正常，上传抽屉的展示由 `hasRunningTasks` 控制。
2. 在有可恢复任务的场景下：
   - 当 `uploadQueue` 中存在 `file === null` 且 `status === 'paused'` 的任务时：
     - `hasRestorableTasks.value` 为 `true`；
     - 页面在 `onMounted` 中会自动打开上传队列抽屉，并提示“检测到上次会话有未完成的上传任务，请为对应任务选择文件继续上传”；
   - 整体行为与之前设计文档中关于“刷新后任务恢复提醒”的描述一致。

## 四、与既有文档和实现的一致性评估

本次修复与以下文档保持一致：

- `docs/specs/文件管理新版_上传功能升级设计_20251120-1858.md` 中对 `useUploadQueue` 的类型定义与 API 约定；
- `docs/changes/文件管理新版_上传队列与直传实现_20251120-1910.md` 中对 `uploadQueue` 为 `ref([])` 的描述；
- `docs/changes/文件管理新版_分片上传与秒传逻辑完善_20251120-1908.md` 与 `docs/changes/文件管理新版_上传暂停大文件哈希与恢复实现_20251120-1925.md` 中有关“任务恢复与 attachFileToTask”的说明。

修复仅作用于 `Explorer.vue` 对组合函数返回值的使用方式，对上传队列内部状态机、秒传/分片逻辑、任务恢复语义均无改动，因此风险极低。

## 五、后续建议

1. **在组合函数返回值上添加类型注解或 JSDoc**  
   在 `useUploadQueue` 中通过简单的 JSDoc 标注 `uploadQueue` 类型为 `Ref<UploadTask[]>`，有助于编辑器提示正确使用 `.value`。

2. **在更多地方统一使用 computed 包装布尔派生状态**  
   类似 `hasRestorableTasks` 的逻辑可以考虑下沉到 `useUploadQueue` 内部，例如导出 `hasRestorableTasks` 或 `restorableTasks`，避免调用方重复编写 `uploadQueue.value.some(...)`，从而降低使用出错概率。

本次修复的目标单一、变更范围小，主要是修正对 `ref` 的误用，消除初始化时报错，为后续围绕上传队列的功能迭代提供更稳定的基础。
